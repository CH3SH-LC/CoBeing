1. 既然工作智能体不主动访问自己的空间，那是否保存记忆和经验、调取记忆和经验这两个任务都可以交给工具或工具智能体完成，不需要工作智能体有自己的空间

2. 主对话窗口是唯一的特例

3. 智能体不会主动被使用，只有被加入群组才可用。也就是睡眠没有意义。销毁就是清空所有内容包括记忆

4. 智能体在工作的时候，比如调用write写内容，这一段是私有记忆。但是写完了成为一个群组空间内的文档，这时候这个文档是可以被别的智能体read工具读取的

5. mention bulter是需要转发，mention user这时候管家根本没有被唤醒，也就不存在转发。另外存在情况mention user,bulter，这时候管家也应该转述

6. label指的是表示成员名称的标签，比如user，bulter，某个具体的工作智能体比如websearcher

7. 默认位置是这个程序的注册位置需要留有data文件夹，里面有group子文件夹，这个group作为默认位置，它的子文件夹分别代表一个群组

8. 任务失败需要找出原因，如果需要或者没有解决办法则需要通知用户（也可以bulter转发）

9. 需求变更可以由管家主动决定是否使用新群组。另外，新群组不一定非要很频繁，比如完成一项任务紧接着完成另一项后续任务，这就可以使用同一个群组

10. 智能体只是一个组织形式，两个群组的同名智能体是完全不同的上下文，可以理解为完全不同的智能体，直接并发。另外，群组内，维护智能体状态，群组内的智能体工作中又被mention，则flag为true，等这个智能体完全工作完再被第二次唤醒

11. 对于膨胀的私密内容，如果总长度过高，则使用新工具智能体【压缩】，等同于常见的压缩，只不过是将私密内容分段压缩

12. 对于私密内容和缓存命中的问题，不存在，真实情况为“智能体1发言-智能体2思考-智能体2发言-智能体1发言-智能体2思考-智能体2发言”新一轮智能体1发言后，智能体2新增的私密内容插在最后，然后发言再插在最后，完全不影响前面的思考或者前缀

13. 公共上下文超长，则需要全量压缩，调用【总结】智能体根据独立上下文总结每个智能体内容，然后调用【压缩】智能体分别压缩公共上下文和每个工作智能体上下文，然后由bulter再次开启工作（这里需要防止压缩完所有智能体都停了）

14. 智能体在唤醒别人的时候，需要明确附上需要别人做什么，防止两个智能体做同样的工作。

15. 允许@all

16. mention失败则需要向调用mention的智能体发起错误反馈，正忙的智能体不会出错，见10

17. 智能体名录由数据库构成，管家调用工具创建销毁智能体或群组的时候工具的另一个工作是编辑数据库

18. 并发与写冲突参考dsh

19. 如果没有明确需求，则不允许创建全量访问的群组

20. 管家有能力进行细化，给群组内的每一个智能体在这个群组内附加权限

21. 用户不在线，若程序关闭，则程序也无法运行，若程序正在运行，则任务栏图标闪烁加发出一声滴

22. 对话列表采用dsh可重建机制

23. 工具智能体类似于tool的发现方式

24. 总结需要严格参考工作智能体的定义，比如一个前端的智能体需要总结用户的前端偏好，但不需要用户喜欢吃甜食这个知识

25. 不需要群主

26. 管家创造保留批准

27. 管家创建智能体需要考虑通用性和专业性，比如一个前端智能体就优于塔防前端智能体，前端智能体优于代码智能体。这里需要单独深度调研

28. 原体规格严格参照dsh

29. GUI必须有，作为主要入口，同时严格拒绝浏览器前端，采用tauri原生桌面

30. 前端设计方案需要深度调研

31. 多任务分配给多群组

32. 管家使用工具参与群组对话

33. 关于管家在主窗口和群组内的差异需要单独澄清

34. 关于与dsh结合，需要参考dsh的插件化，将非必须的功能插件化，核心保留干净。另外，dsh的热重载和隔离机制需要重点学习，如何在一个插件崩溃的情况下不影响全局，别的功能还能正常使用；另一个重点是调度器；别的dsh的小方面比如死亡=工作区隔离也需要学习
