## 1. 使用方式

- **主要方式**：用户直接和管家对话（主对话窗口）。管家对用户需求进行总结、分析、转发，提供给具体工作的智能体或群组。工作智能体/群组工作过程中可随时向用户提问，提问由管家转述给用户。
- **次要方式**：用户直接进入群组，以用户身份发言，直接与群组内智能体对话。
- **多任务**：用户的多项需求分配给多个群组并行。
- **通知**：用户不在线时——若程序关闭则无法运行；若程序正在运行，则任务栏图标闪烁 + 一声滴。

## 2. 群组模型

### 基本结构

- 所有对话窗口都是群组（**主对话窗口是唯一特例**，不是群组）。
- **label = 成员名称标签集合**（如 user、butler、websearcher），label ≥ 3：即每个群组 = user + butler + ≥1 个工作智能体。
- user 代表用户，拥有最高权限；butler 代表管家，权限仅次于用户。
- 群组 = **群组空间 + 群组成员 + 群组窗口**。
- 群组成员 = 工作智能体 + user + butler。
- **不需要群主**。

### 群组空间

- 三种形态：**指定位置** / **默认位置**（`<程序注册位置>/data/group/<群组名>/`，其子文件夹分别代表一个群组）/ **无**（可访问一切地方）。
- **无明确需求时禁止创建全量访问群组**（"无"是受限特例）。
- 管家可为群组内每个智能体**附加细化权限**。

### 群组寿命

- 群组寿命由工作决定。**群组可复用**：完成一项任务紧接着另一项后续任务时可用同一群组；需求变更时由**管家主动决定**是否使用新群组。
- **完成判定链路**：工作智能体完成 → 管家接收群组内消息得知完成 → 管家回报用户 → **用户自行验收** → 用户明确告知管家成功 → 群组归档死亡。
- **任务失败**：找出原因；无解决办法则通知用户（可由管家转发）。
- 群组死亡 → 所有信息归档（记录不清除，可审计）。

### 上下文模型

- 群组维护**统一对话列表**，所有发言按逻辑顺序排列，作为**公共上下文**（采用 dsh 可重建机制）。
- 智能体工作产生的**思考、write 过程内容等是私密内容**，不进入公共上下文。
- **产物共享规则**：write 完成、落盘为群组空间内的文档后，可被群组内其他智能体用 read 工具读取。**共享 = 落盘即共享；思考 = 不落盘即私有。**
- **独立上下文 = 公共上下文 + 自己的私密内容**。组装时私密内容追加在最新位置（自己的发言之前），不影响既有前缀 → 无缓存命中问题。
- **私密内容膨胀**：总长度过高 → 调用工具智能体【压缩】分段压缩。
- **公共上下文超长**：全量压缩流程——①【总结】智能体根据各智能体独立上下文总结每个智能体内容 → ②【压缩】智能体分别压缩公共上下文与每个工作智能体上下文 → ③ 管家再次开启工作（防止压缩完所有智能体都停摆）。

### 唤醒协议

- 通过 `mention [name]` 唤醒（数组，可唤醒多人）；**允许 @all**。
- 唤醒由智能体自己决定，或用户手动 mention。
- **唤醒必须附带任务说明**（明确要对方做什么），防止两个智能体做同样的工作。
- **忙碌排队**：群组内维护每个智能体的状态 flag——工作中被再次 mention 则 flag=true，等其完全工作完再处理第二次唤醒（正忙不报错）。
- **mention 失败**：向调用 mention 的智能体发起错误反馈。
- **mention user**：随时可用（软约束，非硬条件：用户未直接参与群组时通常不建议）；有大量需求需要确认时也应 mention user。mention user 时管家未被唤醒，不存在转发（直连）；`mention user,butler` 同时存在时，管家也应转述。
- **mention butler**：唤醒群组内管家，管家必须进行分析，回传主对话窗口并返回给用户。
- **管家使用工具参与群组对话**（非自由发言，通过工具调用）。

### 协作纪律

- 智能体需要有**角色意识**：考虑自己的角色、自己适合完成的工作部分、是否需要别的智能体协助；涉及协助时，自己需要产出什么、预留什么接口与别人对接、别人需要完成什么。

## 3. 管家

- **主入口**：用户工作的主对话窗口。
- **唯一需要人格化的智能体**：与用户对话时模拟一个真实角色即可。
- **不完成任何具体工作**，承担两项功能：与用户聊天 + 作为用户和具体工作的中转。
- 中转两个方向：用户→群组（转述用户含义给工作智能体，同时 mention 对应智能体开启工作）；群组→用户（转述工作智能体的需求，让用户说得更清楚）。
- **权限**：管家**对所有文件只读**，无权操作任何产物。
- **创造/毁灭智能体与群组**：
  - 创造：**需要用户批准**（2026-08-20 修订：原"无需批准"改为需要批准）。
  - 毁灭：需要用户明确的点击确认。
  - **销毁语义**：销毁智能体的人格经验（清空）、注销数据库条目、不再可被调用，但**不清除对应历史记录**。
- **创建智能体的原则**：考虑通用性与专业性——通用性 > 专业性（如：前端智能体优于塔防前端智能体；前端智能体优于代码智能体）。该策略需单独深度调研。
- 管家创建/销毁智能体或群组的工具，另一个职责是**编辑名录数据库**。

### 管家上下文模型（2026-08-20 落实，参考纯HI/管家.md）

- **双实例独立上下文，互不干扰**：主窗口管家与各群组窗口管家是独立上下文。
- **群组创建**：群组创建时由管家启动，主窗口管家通过工具调用向群组发消息。
- **群组内被 mention**：群组内管家被 mention 时，其上下文组装方式与工作智能体相同（公共上下文 + 私密内容），分析后**通过工具向主窗口管家发送一条消息**；主窗口管家接收到后被唤醒，向用户回复。
- **主窗口上下文管理**：每 **100k token** 上下文归档一次记忆，然后压缩上下文；用户可手动清空（清空之前先总结归档）。
- 开放问题 #1（主对话窗口 vs 群组内差异）**已关闭**。

## 4. 工作智能体（原体）

- **组织形式**：智能体只是组织形式，**按群组实例化**——两个群组的同名智能体是完全不同的上下文，可理解为完全不同的智能体，直接并发。
- **人格记忆共享、上下文不共享**：同名智能体的经验档案按名字全局共享（人格 + 记忆共享），但各群组上下文完全隔离。
- **没有自己的空间**：保存记忆经验、调取记忆经验两个任务交给工具/工具智能体完成，不需要工作智能体有自己的空间。
- **原体规格**：严格参照 dsh 极简模式构建工作智能体【原体】（详见 `v2-原体规格-v0.2.md`）。

## 5. 工具智能体

- 定义：部分固定操作不可硬编码、需要 LLM 参与，但工作内容非常固定 → 工具智能体。智能体像调用工具一样调用工具智能体。
- 发现方式：类似于 tool 的发现方式（注册表/工具列表）。
- **实现形态：半硬编码**（固定流程骨架 + LLM 只参与必要环节）。
- 当前工具智能体：
  - **【总结】**：帮助总结经验和记忆；总结范围**严格参考工作智能体的定义**（如前端智能体总结用户前端偏好，不需要"用户爱吃甜食"这类无关知识）；公共上下文全量压缩时按各独立上下文总结每个智能体内容。
  - **【压缩】**：私密内容分段压缩；全量压缩时分别压缩公共上下文与每个工作智能体上下文。

## 6. 经验与成长

- 所有长久存活的智能体都需要总结经验；**不要吝啬总结**，所有智能体都需要不断进化。
- 管家的经验总结在自己的目录（主对话侧）。
- 工作智能体的经历和经验通过工具/工具智能体总结，**不存放在群组空间**。
- 经验档案按智能体名字全局共享（人格记忆共享），跨群组可用。
- **经验档案存储形态：条目式纯文档 md**（2026-08-20 定稿）——每个智能体一份 Markdown 档案，条目式结构（每条经验一个条目，含时间/来源/内容等字段）；写入方为【总结】工具智能体，读取方经工具调取；**不使用数据库存储经验**。

## 7. 数据与存储

- **名录数据库**：智能体名录由数据库构成；管家创建/销毁工具的副职责是编辑数据库。
- **经验档案**：条目式纯文档 md（每个智能体一份，按名字全局共享，非数据库）。
- **群组空间**：默认 `<程序注册位置>/data/group/<群组名>/`。
- **对话列表**：采用 dsh 可重建机制（append-only 事件日志，支持重放/恢复）。
- **归档**：群组死亡后所有信息归档，记录不清除。

## 8. 权限与安全

- 无明确需求禁止创建全量访问群组。
- 管家对所有文件只读。
- 管家可为群组内每个智能体附加细化权限（读写/工具等粒度待设计）。
- 并发与写冲突：参考 dsh（调度器式执行 + 工作区隔离）。

## 9. GUI

- **GUI 必须有，是主要入口**。
- **严格拒绝浏览器前端，采用 Tauri 原生桌面**。
- 前端设计方案需单独深度调研。

## 10. 参考 dsh 工程机制（v2 技术基调）

1. **插件化**：将非必须的功能插件化，核心保持干净。
2. **热重载与隔离**：重点学习——一个插件崩溃不影响全局，其他功能还能正常使用。
3. **调度器**：工具执行/并发仲裁参考 dsh 调度器。
4. **可重建日志**：对话列表采用可重建机制。
5. **死亡 = 工作区隔离**：群组死亡 = 工作区归档隔离，新任务派生新工作区。
6. **原体**：工作智能体原体规格严格参照 dsh 极简模式。
