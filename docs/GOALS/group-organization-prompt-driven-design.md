# 群组组织与纯 Prompt 协作 - 设计文档

> 日期：2026-06-08 | 状态：已确认方向

## 背景

CoBeing 的群组不应被设计成一次性任务容器。它更像用户长期拥有的场景空间，例如“旅行群”“学习群”“产品群”“家庭事务群”。一个群组可以承接很多次具体工作，但群组本身长期存在，沉淀成员配合方式、公共记忆、资源偏好和场景经验。

前面的管家设计已经明确：管家是用户主入口和跨空间调度层；通用智能体设计已经明确：Agent 是长期存在、可被调度的专业 AI 联系人。群组这一维度要解决的是：多个 Agent 在同一个长期场景空间内如何协作、如何受控、如何不互相打断，又如何在需要用户判断时停下来。

本设计采用用户确认的方向：**纯 prompt 驱动**。也就是说，不把群组协作做成重协议状态机，不要求每一步都靠结构化协议推进；但会把群主职责、Agent 行为边界、协作判断点、用户审批点和工具使用方式写进群组 prompt、群主 prompt、Agent 群组上下文和 GUIDE 类规则中。

## 已确认设计决策

| 维度 | 决策 |
| --- | --- |
| 群组定位 | 长期存在的场景空间，不是单个任务容器 |
| 群主概念 | 明确保留“群主”，定位为群组责任协调者 |
| 协作驱动方式 | 纯 prompt 驱动，不引入重协议工作流作为前置条件 |
| 用户入口 | 用户既可通过管家进入群组，也可直接进入群组 |
| 群主职责 | 启动、唤醒、恢复、收束、资源申请、决策体验、TODO 和公共记忆维护 |
| Agent 角色 | 受边界约束的专业执行者，不是完全自主决策者 |
| Agent 自主性 | 可以反复调用 LLM 和工具推进工作，但必须在决策点、协作点、资源点停下来 |
| 中途协作 | Agent 可在工作中途用群组消息唤醒他人，同时继续自己的工作 |
| 群组工作区 | 产品层面保留最小必要记录，不让用户面对大量文档 |
| 与管家关系 | 群组关键事件可回传管家，但群组内部过程默认不刷屏管家 |

## 目标

1. 把 Group 明确定义为长期场景空间。
2. 明确群主的产品概念、权限和职责边界。
3. 明确群组内 Agent 如何发挥专业功能而不过度自主发挥。
4. 明确 Agent 什么时候继续独立工作，什么时候请用户判断，什么时候请其他 Agent 协作，什么时候申请 Skill、Plugin 或新 Agent。
5. 明确多 Agent 协作中“中途发消息唤醒别人但自己继续工作”的机制。
6. 保持群组协作主要由 prompt 规则驱动，避免过度协议化。
7. 降低用户决策负担，让群主把群组内部复杂性压缩成用户能回答的问题。

## 非目标

1. 不把群组变成企业项目管理系统。
2. 不把每个群组绑定到一个固定目标或固定任务。
3. 不要求每个协作步骤都写入结构化协议。
4. 不让普通 Agent 静默替用户做设计、预算、风格、授权等主观或高风险决策。
5. 不让 Agent 静默安装 Skill、Plugin 或 Market 资源。
6. 不要求用户阅读群组内部所有讨论。
7. 不在本设计中实现代码，只形成后续统一实施的设计依据。

## 群组定义

群组是一个长期存在的场景空间，承载一组围绕同类需求协作的 Agent、群主、公共记忆、工作区和 TODO。

群组不是：

- 不是一次性任务。
- 不是企业部门。
- 不是聊天房间的简单转发器。
- 不是让所有 Agent 自由发挥的开放讨论区。

群组是：

- 一个可以被管家调度的执行空间。
- 一个用户可以直接进入的协作空间。
- 一个可以持续沉淀公共记忆的场景容器。
- 一个让多个专业 Agent 按需协作的运行环境。

例如，“暑假去日本七天怎么玩”不是群组，而是“旅行群”里的一个具体工作回合。这个工作结束后，旅行群仍然存在，后续可以继续处理签证、酒店、行李、周末出行、亲子旅行等需求。

## 总体架构

推荐结构如下：

```text
User
  ├─ 通过 Butler 提出需求
  │    └─ Butler 派发到 Group，并维护全局 TODOboard / ButlerTask
  │
  └─ 直接进入 Group 提出需求

Group 长期场景空间
  ├─ HostAgent / 群主
  ├─ Member Agents
  ├─ WakeSystem
  ├─ Group Context / History
  ├─ Group TODOboard
  ├─ Public Memory / Experience
  ├─ Minimal Workspace
  └─ Prompt Rules / GUIDE
```

这套架构中，WakeSystem、TODO、工具、记忆和工作区是运行承载；真正决定“谁该做什么、什么时候该停、什么时候该问用户”的，是 prompt 规则、群主的组织判断和任务承担 Agent 的局部判断。

因此本设计不是“无结构”，而是“轻结构 + prompt 决策”：

- 结构用于承载：消息、唤醒、TODO、记忆、工具。
- prompt 用于判断：是否需要用户、是否需要协作、是否需要资源、是否应该继续。
- 群主判断工作回合、成员分工、依赖路由和用户决策体验；每个 TODO 是否自然续作，应由承担该 TODO 的 Agent 先判断，再由群主承接跨成员、跨群组或需审批的后续请求。

## 群主概念

群主是群组的责任协调者，是长期场景空间里的常驻运行核心。

群主不是普通群成员，也不是强人格老板。群主的权力来自责任：它对用户负责，对群组秩序负责，对任务推进负责，对结果收束负责。

最终定义：

> 群主是群组对用户负责的运行接口。它负责启动、组织、恢复、收束和沉淀群组协作。它不是群组里的上级，也不是万能执行者，而是保证群组不会失控、不会沉默、不会丢上下文、不会把决策负担原样丢给用户的协调智能体。

### 群主核心职责

1. **标记任务开始与结束**
   - 用户或管家提出需求后，群主判断是否形成一个具体工作回合。
   - 工作开始时说明目标、边界和预期产物。
   - 工作结束时整合结果、标记完成、提示下一步。

2. **介入启动并唤醒智能体**
   - 群主决定唤醒谁，而不是默认 @all。
   - 防止一窝蜂唤醒所有 Agent。
   - 防止没有任何 Agent 被唤醒。

3. **恢复停滞工作**
   - 当任务未完成但没人工作、TODO 停滞、成员卡住或上下文断掉时，群主应被唤醒。
   - 群主负责重启工作、重新分配、追问阻塞原因或申请资源。

4. **对用户负责并整合结果**
   - 群主不是把所有成员回复堆给用户。
   - 群主应把群组工作压缩成摘要、选项、推荐和交付物。

5. **申请更多资源**
   - 群组缺 Agent、Skill、Plugin、工具权限或 Market 模板时，群主代表群组向用户或管家申请。
   - 群主不能静默安装高风险资源。

6. **清理智能体和协作噪音**
   - 对临时加入、明显不适合、长期不工作的成员，群主可以建议移除或替换。
   - 涉及删除用户长期 Agent 时必须请求用户或管家确认。

7. **优化用户决策体验**
   - 当群组需要用户判断时，群主负责把内部问题转成少量可选方案。
   - 群主应给出推荐理由，而不是让用户读完整讨论。

8. **维护群组 TODOboard**
   - 群主负责创建、分配、检查、恢复和收束群组 TODO。
   - 普通 Agent 可以更新自己负责的 TODO，但不应随意重排整体任务。

9. **维护群组公共记忆**
   - 群主负责沉淀关键决策、用户偏好、协作经验、资源选择和失败教训。
   - 不要求记录所有聊天内容。

### 群主触发时机

群主应在以下场景被唤醒：

- 用户直接在群组提出新需求。
- Butler 派发任务到群组。
- Agent 通过群组消息请求仲裁、协作或资源。
- 任务长时间未完成且没有 Agent 工作。
- TODO 到期、阻塞或无人认领。
- 成员分歧持续 2 轮以上。
- 出现需要用户确认的设计稿、方案、预算、权限或范围变化。
- 群组完成主要交付，需要收束给用户或 Butler。

### 群主与管家的区别

| 角色 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| Butler / 管家 | 用户主入口、跨空间调度、全局任务托管、关键事件回传 | 不旁听所有群组过程，不替群组内部持续主持 |
| Host / 群主 | 群组内部协调、唤醒、恢复、结果整合、公共记忆 | 不成为用户唯一入口，不管理所有群组 |
| Agent / 成员 | 专业执行、局部判断、产出具体成果 | 不越权替用户做关键决定，不静默扩权 |
| TODOboard | 状态账本 | 不承担智能责任 |

## 纯 Prompt 驱动策略

纯 prompt 驱动不是“不设计规则”。它的含义是：群组协作的主要判断由 LLM 根据 prompt、上下文、角色职责和工具说明完成，而不是依赖一套强制状态机。

推荐把规则写入四个层级：

1. **群组 GUIDE / 群组规则**
   - 定义本群组的场景、成员边界、协作风格、用户审批点。

2. **群主 JOB / 群主职责 prompt**
   - 定义群主如何启动任务、唤醒成员、追踪 TODO、申请资源和收束结果。

3. **Agent 群组上下文**
   - 在每次群组唤醒时告诉 Agent：当前群组是谁、成员能力、当前 TODO、协作规则、用户审批规则。

4. **工具说明**
   - 明确 `group-send`、TODO、经验沉淀、资源申请等工具应该在什么情况下使用。

纯 prompt 驱动的边界：

- 可以使用结构化模板帮助 LLM 表达协作消息。
- 可以使用现有 WakeSystem、TODO 和工具作为承载。
- 不把每个动作都变成必须通过固定协议校验。
- 不让用户面对复杂流程图。
- 不把群组变成企业流程软件。

## 群组内 Agent 协作

群组内 Agent 是受边界约束的专业执行者。

它可以：

- 根据自己的 JOB 独立分析和执行。
- 反复调用 LLM 与工具推进工作。
- 在工作中途向群组发送协作消息。
- @mention 其他 Agent 请求并行协助。
- 完成后汇报结果、证据和产物。
- 发现能力缺口时请求群主申请资源。

它不应该：

- 自行替用户审批设计稿、方案、预算或风格。
- 自行扩大任务范围。
- 自行安装 Skill、Plugin 或 Market 资源。
- 把所有中间想法都发到群组。
- 在自己领域无关时强行参与。
- 用最终回复承担唤醒别人这种路由职责。

### Agent 的判断框架

每个 Agent 在群组内被唤醒后，应按以下顺序自查：

1. **这件事是否属于我的职责？**
   - 属于：继续执行。
   - 不属于：保持安静，或建议更合适的 Agent。

2. **我能否在当前信息下继续？**
   - 能：使用工具推进。
   - 不能：说明缺什么。

3. **是否需要用户判断？**
   - 设计稿、方案、预算、风格、范围、权限、关键验收等需要用户判断。
   - 这类情况应通知群主，由群主整理给用户或管家。

4. **是否需要其他 Agent 协作？**
   - 涉及别人的专业领域、上下游依赖、并行子任务、审查或冲突时，需要协作。
   - 使用 `group-send` @mention 对方，并清楚说明请求。

5. **是否需要更多资源？**
   - 缺 Skill、Plugin、工具、Agent、权限或外部模板时，向群主说明资源缺口。

6. **是否已经完成可交付结果？**
   - 完成后汇报产物、证据、限制和下一步建议。
   - 不要只说“我完成了”，要说明完成了什么。

### 需要用户判断的典型场景

以下场景 Agent 不应自行拍板：

- 设计稿、视觉方向、品牌风格需要审批。
- 多个可行方案之间存在主观偏好。
- 预算、时间、风险或成本明显变化。
- 任务范围扩大或目标改变。
- 需要用户隐私、账号、付款、授权或外部访问。
- 产物已到阶段性验收点。
- 群组内部无法判断哪种取舍更符合用户偏好。

推荐行为：

```text
@host 当前已形成两个设计方向，需要用户审批后继续：
1. 可信专业：信息密度高，更适合 B 端客户
2. 轻松生活化：更亲和，更适合普通消费者

我建议让用户先选方向，再继续细化视觉稿。
```

### 需要其他 Agent 协作的典型场景

以下场景 Agent 应主动请求协作：

- 当前任务有明确的专业分工。
- 自己完成上游后，需要下游继续。
- 自己可以继续做一部分，但另一部分可并行。
- 需要审查、校对、测试、事实核查。
- 讨论超过两轮仍无共识。
- 自己发现能力不匹配。

推荐行为：

```text
@视觉设计师 我正在整理落地页文案，需要你并行出 2 个首屏视觉方向。
重点比较“可信专业”和“轻松生活化”两种气质。
我会继续整理信息架构，不等你完成。
```

### 需要申请更多 Skill 的典型场景

以下场景 Agent 应请求群主申请 Skill 或其他资源：

- 现有成员缺少稳定方法论。
- 任务明显需要专门流程，例如竞品调研、代码审查、旅行规划、图片处理。
- Agent 多次尝试仍无法达到质量要求。
- 需要外部工具、MCP、Plugin 或 Market 模板。
- 群组内没有合适成员。

推荐行为：

```text
@host 这个任务需要系统化竞品调研 Skill。当前我可以做基础搜索，但缺少稳定的信息抽取和对比框架。
建议向用户申请启用或安装“竞品调研”相关 Skill。
```

## 非阻塞协作消息

多 Agent 协作中，一个 Agent 经常需要在工作中途唤醒别人，但又不能因为发了一条消息就停止自己的任务。

现有运行机制已经具备基础：

- Agent 在单次 `ConversationLoop.run()` 中可以多轮调用 LLM 和工具。
- `group-send` 是工具，Agent 可以在工具循环中调用它。
- `group-send` 调用 `group.postMessage()`，会触发 WakeSystem 扫描 @mention。
- WakeSystem 是异步唤醒队列，可以在后续 tick 唤醒其他 Agent。
- 原 Agent 调用完 `group-send` 后，仍可以继续自己的 LLM / 工具循环。

因此设计口径应明确：

> `group-send` 是协作旁路消息，不是最终回复。Agent 用它在工作中途发起协作、上报阻塞、请求审批或申请资源；发送后默认继续自己的工作，除非消息内容明确表示需要暂停等待。

### 协作消息的 prompt 规则

Agent 使用 `group-send` 时应说明：

- 当前自己正在做什么。
- 需要对方做什么。
- 对方输出会被如何使用。
- 是否需要立刻回复。
- 自己是继续工作，还是暂停等待。

推荐模板：

```text
@目标Agent
我正在做：...
我需要你：...
你的输出会用于：...
我会：继续推进 / 暂停等待 / 先完成我的部分
```

### 最终回复与协作消息的区别

群组内必须区分两类输出：

1. **协作消息**
   - 通过 `group-send` 发出。
   - 可以 @mention 并唤醒其他 Agent。
   - 用于中途协作、阻塞、审批、资源申请。

2. **最终回复**
   - 是本轮 Agent 被唤醒后的最终结果。
   - 由 WakeSystem 写回群组上下文。
   - 不应承担“唤醒别人”的主要职责。

这条规则很重要：如果 Agent 想让别人接力或协作，应使用 `group-send`，不要只在最终回复里写一个 @mention。

## 群组 TODOboard

群组 TODOboard 是群组内部执行账本，不替代全局 TODOboard。

推荐分工：

- 全局 TODOboard：记录用户交给系统的任务，接受者可以是 Agent 或 Group。
- 群组 TODOboard：记录群组内部拆解出来的子任务、依赖、负责人和状态。
- Agent TODO：记录单个 Agent 的个人执行任务。

群主对群组 TODOboard 有较高管理权限：

- 创建任务。
- 分配任务。
- 检查过期任务。
- 重新唤醒或重新分配。
- 标记工作回合完成。
- 清理无效任务。

这种管理权限不等于替成员判断续作。群组 TODO 完成时，应先由被指派的承担 Agent 判断是否需要下游任务、复查任务、验收任务或资源申请；群主负责把这个判断路由成可执行的组内 TODO、用户问题或回传 Butler 的跨空间请求。

普通 Agent 可以：

- 查看与自己相关的 TODO。
- 更新自己负责的 TODO。
- 完成后汇报结果。
- 发现 TODO 不合理时提醒群主。

普通 Agent 不应随意重排整个群组任务计划。

## 公共记忆

群组公共记忆只沉淀对长期场景有价值的信息：

- 用户偏好。
- 关键决策。
- 成员协作方式。
- 资源选择。
- 已验证有效的方法。
- 失败教训。
- 常见审批偏好。

不需要沉淀：

- 每条普通聊天。
- 工具日志。
- 临时草稿。
- 无价值争论。
- 成员私有记忆。

群主是公共记忆的主要维护者。普通 Agent 可以提出经验，但群主应负责去重、压缩和判断是否值得进入公共记忆。

## 最小工作区

用户已经明确：群组工作区不需要很多文档记录。

因此产品口径应采用最小工作区：

- `config.json`：群组配置，内部使用。
- `GUIDE.md` 或等价 prompt 规则：群组场景、成员规则、用户审批点。
- `TODO.json`：群组内部任务账本。
- `EXPERIENCE.md` 或公共记忆摘要：长期场景经验。
- `context.jsonl` / SQLite：内部历史和检索，不作为用户主要界面。
- `workspace/`：真实产物和工作文件。

旧有的 `TASK.md`、`PLAN.md`、`PROGRESS.md`、`INTERFACE.md` 等可以作为内部实现兼容或特定工作回合的临时文件，但不应成为普通用户理解群组的核心负担。未来实现时可逐步弱化这些文件在产品表层的存在感。

## 用户直接进群与通过管家进群

### 用户通过管家进入

1. 用户向 Butler 提出需求。
2. Butler 判断需要群组处理。
3. Butler 创建或关联全局 TODOboard 条目。
4. Butler 将任务派发到目标 Group。
5. 群主启动工作回合。
6. 群组只在关键节点回传 Butler。
7. Butler 向用户呈现审批问题、进度摘要或最终结果。

### 用户直接进入群组

1. 用户在群组里提出需求。
2. 群主直接接住并判断是否启动工作回合。
3. 群主可以直接问用户确认。
4. 如果任务需要全局追踪，群主或系统应同步到全局 TODOboard。
5. 如果需要跨群组资源、Market 或敏感授权，群主应请求 Butler 或用户确认。

两种路径都合法。区别是：通过 Butler 进入时，Butler 是用户主入口；直接进群时，群主承担现场对话和协调。

## 与现有实现的关系

当前代码已经提供若干基础：

- Group 已有长期对象、成员、群主和 WakeSystem。
- WakeSystem 已支持 @mention 队列、异步 tick、处理中的 Agent 防并发。
- Agent 群组模式已有独立 ConversationLoop。
- Agent 可以在一次 run 中反复调用 LLM 和工具。
- `group-send` 已能在工具循环中向群组发消息，并通过 @mention 唤醒他人。
- 群组上下文已能注入成员、TODO、经验和协作规则。
- 已有 Review Tool Agent 可用于约束偷懒式或低质量发言。

因此后续实现的重点不是重写群组引擎，而是重写和收敛 prompt 体系：

- 群主 JOB。
- 群组 GUIDE。
- Agent 群组上下文规则。
- `group-send` 工具说明。
- 用户审批点规则。
- 资源申请规则。
- 公共记忆沉淀规则。

## 边界情况

### Agent 过度自主发挥

通过 prompt 明确：涉及用户偏好、审批、预算、授权、范围变化时必须找群主或用户。Review Agent 可作为辅助约束，但核心仍是 prompt 规则。

### Agent 只说要做但不做

群组规则应要求：发言前先完成可完成的工作。没有实际产出时不要只宣布意图。现有 Review 机制可继续用于拦截偷懒式群组消息。

### 没有 Agent 被唤醒

群主应被唤醒并判断谁应该参与。群主不能只等待成员自发行动。

### 太多 Agent 被唤醒

群主应避免默认 @all。只有需要全员输入时才 @all。否则按专业能力点名。

### Agent 中途请求协作但自己停住

prompt 中应明确：`group-send` 默认是非阻塞协作消息。除非明确依赖对方结果，否则发送后继续自己的部分。

### Agent 需要对方结果才能继续

Agent 应说明自己暂停等待，并让群主或 TODO 记录依赖。对方完成后，群主或 TODOboard 再唤醒它。

### 群组缺少合适能力

Agent 不能静默安装资源。它应向群主说明能力缺口。群主再向用户或管家申请 Agent、Skill、Plugin 或 Market 资源。

### 群组 TODO 完成后是否继续

承担该 TODO 的 Agent 先判断是否存在自然后续。低风险、明确承诺、强依赖的后续可以请求创建组内 TODO；涉及用户选择、授权、付款、隐私、范围扩大或跨群组路由时，交给群主或 Butler 上浮。群主负责协调和审批路径，不替承担 Agent 判断“是否还有下一步”。

### 任务完成但用户未验收

如果成果涉及设计、方案、预算、内容风格或其他主观判断，应标记为“待用户确认”，不能直接视为最终完成。

## 后续实施方向

后续统一进入实现时，建议优先做 prompt 与配置层更新：

1. 重写群主核心 prompt，明确责任型群主。
2. 重写群组协作规则，加入用户审批点、协作点和资源申请点。
3. 重写 Agent 群组上下文中的行为规则，限制过度自主发挥。
4. 强化 `group-send` 工具说明，明确它是非阻塞协作消息。
5. 弱化工作区文档在产品表层的存在感，保留内部兼容。
6. 为典型场景写验收用例：设计稿审批、并行协作、资源申请、停滞恢复、群主收束。

## 验收方向

后续实现时至少需要验证：

1. 用户在“旅行群”提出具体旅行需求，群主启动一次工作回合，而不是创建新一次性群组。
2. 群主只唤醒相关 Agent，不默认一窝蜂 @all。
3. Agent 生成设计稿后会请求用户审批，而不是自己继续定稿。
4. Agent 工作中途可以用 `group-send` @mention 其他 Agent，同时继续自己的工具循环。
5. 被 @mention 的 Agent 能被 WakeSystem 异步唤醒。
6. Agent 发现缺 Skill 时向群主申请，而不是静默安装。
7. 群主能把多个 Agent 的结果整合成用户可读交付。
8. 任务停滞时群主能被唤醒并恢复推进。
9. 普通群组过程不会主动刷屏 Butler。
10. 通过 Butler 派发的群组任务在关键节点能回传 Butler。

## 最终口径

群组是长期场景空间，不是任务容器。

群主是群组的责任协调者，不是老板，也不是普通成员。它负责启动、唤醒、恢复、收束、资源申请、决策体验、群组 TODO 和公共记忆。

群组内 Agent 是受边界约束的专业执行者。它可以独立反复调用 LLM 和工具，但不能替用户做关键决策，不能静默扩权，不能在需要协作时硬做。

多 Agent 协作采用纯 prompt 驱动：不引入重协议状态机，但通过群组规则、群主职责、Agent 群组上下文和工具说明，让 Agent 知道什么时候继续工作、什么时候问用户、什么时候找队友、什么时候申请资源。

`group-send` 是群组协作的关键旁路能力。Agent 可以在工作中途用它唤醒别人，同时继续自己的工作。这让群组从“轮流聊天”升级为“异步协作”。
