# CoBeing 架构说明

> 最后更新：2026-08-09  
> 本文档解释当前代码中的真实架构，不沿用旧版能力清单。

---

## 总体架构

CoBeing 的代码结构可以分为五层：

1. 后端运行时层：负责 Agent、Butler、Group、Tool、Memory、Plugin、MCP、Channel、WebSocket 的启动与编排。
2. 智能体层：Agent、Butler、Group 组成核心 Agent Team 范式。
3. 扩展层：Provider、Channel、Skill、Plugin、MCP 负责外部能力接入。
4. 数据层：`data/` 下保存 Agent、Group、skills、plugins、runtime registry、记忆与工作区。
5. GUI 层：React/Tauri 前端通过本地 WebSocket 调用后端能力。

整体是本地优先架构，用户数据主要保存在本机 `data/` 目录。

SQLite 相关模块采用“优先真实 SQLite，失败降级”的策略：项目当前使用 `better-sqlite3@12.10.0`，可在 Node 24 下加载原生 binding；`memory/SqliteAdapter` 与 `observability/ObservabilityDB` 在 SQLite 不可用时使用同路径 JSON fallback，`group/GroupDB` 与 `group/GroupAgentMemory` 使用内存 fallback。该策略用于避免 Node/native binding 异常时启动失败，但正常路径仍是 SQLite/FTS5。

## 后端包结构

### `packages/core`

核心运行时包，承担系统主体职责。关键模块包括：

- `runtime.ts`：CoBeingRuntime 顶层编排器
- `agent/`：Agent、Butler、AgentRegistry、AgentPaths、ToolAgent
- `group/`：Group、GroupManager、GroupContextV2、WakeSystem、群组记忆
- `conversation/`：会话循环、PromptBuilder、LLM 调用流程
- `tools/`：工具注册、权限执行、沙箱、内置工具
- `memory/`：MemoryStore、SQLite adapter、安全扫描、经验存储
- `todo/`：Agent/Group TODO、扫描器、触发机制
- `api/`：WebSocket server 与 GUI 命令处理
- `mcp/`：MCP client、manager、transport、bridge tool
- `observability/`：运行指标、活动记录、仪表盘数据

### `packages/shared`

跨包共享能力，包括类型定义、事件、日志、文件工具、常量和 master registry。

### `packages/providers`

Provider 接口和 OpenAI-compatible 基类。当前内置代码层主要包含 DeepSeek catalog，更多 Provider 通过 `data/plugins/providers/` 的数据插件扩展。

### `packages/channels`

Channel 接口和 QQ Bot 通道实现。默认配置中 channels 为空，QQ Bot 是可选接入。

### `packages/plugin-sdk`

插件 SDK，包括 manifest 类型、插件加载器、HookBus、PromptLayerRegistry、UIExtensionRegistry。它为 Provider、Channel、UI 扩展和运行时 hook 提供基础设施。

### `packages/mcp-servers`

内置 MCP server 包，目前包含：

- `qqbot`（2026-08-12 接入 runtime：config mcpServers 已启用 + access_token 鉴权修复 + stdout 纯净修复）
- `office`
- `claude-code`
- `browser`（2026-08-12 新增：Playwright 浏览器自动化，9 工具 + 登录态持久化 storageState 存 data/mcp/）

它们是可接入能力，不代表默认启动时自动连接——但 `claude-code`、`qqbot`、`browser` 三个已在 `config/default.json` 的 `mcpServers` 中启用（runtime 启动时自动连接并注册工具）。

## Runtime 启动链路

`CoBeingRuntime` 的职责是把分散的包和数据目录组织成一个可运行系统。

典型启动逻辑包括：

1. 读取配置与环境变量。
2. 初始化 `data/` 目录和 registry。
3. 检查 Docker 沙箱可用性。
4. 加载 Provider 与插件。
5. 初始化 Butler 和默认 Agent。
6. 初始化 GroupManager 并恢复已有 Group。
7. 启动 TODO 扫描器。
8. 启动 MCP manager。
9. 启动 WebSocket server。
10. 启动可选 Channel。

上述链路在 `runtime.ts`（2026-08-11 从 1734 行拆至 ~860 行）中以多个职责清晰的私有辅助方法承载：`setupGlobalErrorHandlers()`、`checkDockerAvailability()`、`loadAllPluginsStep()`、`createCoreAgents()`、`restoreRegistryState()`、`setupMCP()`、`restoreGroups()`、`configureWSServer()`（收敛 wsServer 的 8 个 setter）、`setupRouterCallbacks()`、`startServices()`、`startTodoScanner()`、`ensureRuntimeDirs()`；`stop()` 有对称的清理方法。各域实现体已提取到 `runtime/` 辅助模块（方法保留薄转发，测试零改动）：`plugin-loader.ts`（插件加载）、`providers.ts`（Provider 构建）、`market.ts`（Market 服务）、`channels.ts`（Channel 生命周期）、`core-agents.ts`（ensureButlerDir/ensureHostDir/createButler/registerPrebuiltAgents/restoreAgents + CoreAgentsLifecycle）。沙箱降级纯函数 `ensureSandboxConfig` 位于 `runtime/sandbox-helper.ts`。

Runtime 是当前系统事实上的“平台内核”。GUI、Butler、Agent、Group、插件和 MCP 都围绕它运行。

## Agent 架构

### Agent 文件系统

每个 Agent 都有自己的目录和核心文件。当前版本的文件职责是：

- `AGENTS.md`：运行规则、工具规则、群组规则、红线
- `EXPRESSION.md`：人味表达规范（篇幅/句式/禁语/真人信号，**无身份设定**；2026-08-05 起取代 CHARACTER.md；历史 Agent 无 EXPRESSION 时兼容 CHARACTER.md）
- `JOB.md`：工作职责和方法论
- `MEMORY.md`：独立会话记忆入口
- `EXPERIENCE.md`：长期经验和用户偏好沉淀
- `config.json`：模型、权限、工具、沙箱、技能白名单

旧版冗余 Agent 文件已经被删除，不能再作为当前架构描述。

### Prompt 构建

PromptBuilder 当前围绕五文件体系工作。它会组合静态规则、项目规则、Agent 人味表达规范、工作职责和动态上下文。

这个设计让“怎么说话”和“怎么工作”分离：

- `EXPRESSION.md` 影响表达方式（仅管家 Butler 走 CHARACTER.md 人格兼容路径）
- `JOB.md` 影响任务处理方式
- `AGENTS.md` 约束边界和工具使用

### 会话循环

Agent 的对话由 ConversationLoop 驱动。它负责构造 prompt、调用 Provider、处理工具调用、写入消息和返回结果。

群组唤醒场景的防"只说不做"机制（2026-08-05 修复）：
- **群组工作推回**：群组成员（具备 write-file/edit-file 工具者）以文本承诺/空响应结束但未产出文件时，注入「立即调用 write-file 产出交付物」指令继续循环（上限 2 次/run，每次 run 重置计数器）；host 等协调者无写工具不受影响。
- **思考轮继续**：推理模型（deepseek-v4-flash）只产出 reasoning 未产出正文时视为思考轮继续循环（上限 3 轮），不再把空输出当最终回复。
- **工具结果截断**：历史中的工具结果截断至 8000 字符，防止大文件读写撑爆上下文。
- **chat 调用 maxTokens=8192**：修复 provider 默认 4096 截断大参数工具调用（如 write-file 携带完整文件内容）导致模型无限"思考"但发不出调用的问题。

工作目录纪律（2026-08-08 修复）：
- **fail-fast**：ConversationLoop 执行工具时若会话工作目录（workingDir）缺失，直接拒绝执行并返回明确错误——绝不静默兜底 `process.cwd()`（曾导致 grep 从项目根全盘扫描、堆耗尽崩溃）。
- **群组工作目录兜底**：wake-system 唤醒群组成员时优先传群组 workspace，取不到时兜底 Agent 自身 workspace，杜绝 undefined 泄漏。
- **扫描上限**：grep/glob 最多遍历 2000 文件 / 12 层目录，grep 单文件 2MB 跳过，超限返回"已截断"提示。
- **路径误用防护**：文件工具（read/write/edit/glob/grep）接入 path-guard，拦截 `data/`、`coreagents/` 等数据目录段前缀路径。

LLMGateway 自 2026-08-09 起为**全局必经链路**：所有 LLM 调用（会话循环、ToolAgent、记忆提取/反思、技能加载/执行、工作流、筛选、续作判断等 17 个调用点）统一经过 `gateway/llm-gateway.ts`（队列 + RPM 限流 + 超时 + 重试），通过 `__cobeing.gateway` 挂载；无全局 gateway 时（单元测试/独立使用）自动降级为直接调用 provider。gateway 不绑定 provider（调用方显式传入，保留会话循环的 fallback 链与熔断器语义）。

## Butler 架构

Butler 是特殊 Agent，位于用户入口层。

2026-08-04 起，管家具备完整的产品化底座：

- **文件体系**：`ensureButlerDir()` 首次启动创建 `data/coreagents/butler/`（config.json + AGENTS/CHARACTER/JOB/MEMORY/EXPERIENCE.md，已存在不覆盖）；管家 prompt 从固定 systemPrompt 改为文件 prompt（与普通 Agent 同构，EXPERIENCE.md/记忆真实进入 prompt，每次运行实时重读）。
- **人格模板**：`templates/butler/personas/` 4 人格（亲密朋友/专业秘书/学习陪伴/家庭助理）×（CHARACTER.md + JOB.md）；`butler_set_persona` 复制切换；`butler_update_style` 把称呼/欢迎语写入 CHARACTER.md「用户偏好」段。JOB.md 承载分级转接规则（自己答/派发/先问用户）与 Market 推荐纪律（低打扰）。
- **转接回执**：`butler_task_updated` 广播携带 `ButlerTaskReceiptPayload`（butlerTaskId/title/targetType/status/summary/nextAction 等，`buildButlerTaskReceiptPayload()` 组装，视图缺失降级 timestamp）；前端聊天流渲染 TaskReceiptCard 并复活 butlerTasks store；`dispatch_task` WS 命令支持 agent/group 双目标 + notifyTarget 透传。
- **首次引导**：`onboarding_apply` 命令（兴趣→角色映射→Creator 生成 1-2 初始 Agent，失败模板 fallback；Market 官方推荐 ≤2 条；data/onboarding.json 幂等）配套前端 OnboardingOverlay 问卷与首启欢迎消息。

它的核心职责是：

- 与用户对话
- 管理 Agent
- 管理 Group

代码中 Butler 已注册多种管理工具，例如创建/销毁 Agent、创建/销毁 Group、修改 Agent 文件、绑定工作区、操作 TODO、向群组发送消息等。

这让 Butler 可以把对话体验优化为“像一个人”，而把具体任务转交给专门 Agent 或 Group。

2026-06-10 起，Butler 具备一条后端可追踪任务派发链路：`dispatchButlerTask()` 会把用户意图落成 Global TODO、ButlerTask、执行引用，并在目标侧创建 Agent inbox item 或 Group TODO。Butler 工具层提供 `butler-dispatch-to-agent`、`butler-dispatch-to-group`、`butler-get-work-status`、`butler-cancel-work`、`butler-reply-to-group`，旧 `butler-dispatch-task` 保留为 Agent 派发兼容入口。

这条链路目前解决的是“托管账本和状态同步”，还不等于完整产品体验。Group -> Butler 的结构化事件工具、用户决策回流、前端任务回执数据流仍需要继续完善。

## Group 架构

Group 是 CoBeing 的多智能体协作单元。

关键组成包括：

- `GroupManager`：创建、恢复、销毁和查询 Group
- `Group`：群组对象和消息入口
- `GroupContextV2`：群组上下文管理
- `WakeSystem`：@mention 后的事件驱动唤醒
- `GroupDB`：群组消息与状态存储
- 群组工作区：最小工作区策略（GUIDE.md + EXPERIENCE.md 自动创建，其余按需生成）
- 群组记忆：Agent 在群组中的上下文和经验

Group 的核心交互机制是：用户或 Agent 向群组发送消息，消息中的 @mention 会进入唤醒队列，被唤醒成员读取上下文并回复。

**协作策略**（2026-06-09）：采用纯 prompt 驱动，不依赖重协议状态机。规则分布在四个层级：
1. `GUIDE.md` — 群组规则模板（场景定义、审批点、资源申请链、禁止行为）
2. `HOST_JOB.md` — 群主职责模板（9 项核心职责、触发时机、判断框架），位于 `templates/host/`
3. Agent 群组上下文 — 6 步判断框架注入到 `buildGroupCollaborationContext()`
4. `group-send` 工具描述 — 非阻塞协作旁路消息

## ToolAgent 架构

ToolAgent 是后台临时工作单元。它与普通 Agent 不同：不进入 AgentRegistry，不出现在普通 Agent 列表，不拥有长期人格和长期任务责任。

当前代码中 ToolAgent 相关文件集中在 `packages/core/src/agent/tool-agent/`：

- `base.ts`：独立 LLM 工具循环和 `data/toolagents/<type>/` 配置读取。
- `types.ts`：ToolAgent 类型、运行配置、结果类型和 `ToolAgentSpec`。
- `spec.ts`：统一配置卡 loader，合并数据目录中的 config/prompt 与默认策略。
- `creator.ts`：Creator ToolAgent，支持 Agent 核心文件生成和 Group 创建草案。
- `memory.ts`：Memory ToolAgent，返回经验条目、`MEMORY.md` 修改建议和风险警告。
- `review.ts`、`judgment.ts`、`clone.ts` 以及能力/成长/归档相关 ToolAgent。

`ToolAgentSpec` 记录触发来源、可见性、写入策略和失败策略。默认边界是：ToolAgent 返回结构化结果，由调用方应用；能写入长期文件的场景也必须由调用方决定，不让 ToolAgent 自己成为长期记忆或资源管理主体。

Group 创建链路已经接入 Creator ToolAgent：WebSocket `create_group` 创建群组后，会生成并写入 `GUIDE.md` / `PLAN.md` 草案，同时把成员缺口、初始任务和用户确认问题交给 host 继续向用户确认。

## Tool 与权限架构

工具系统由三部分组成：

- `ToolRegistry`：注册工具定义
- `ToolExecutor`：执行工具调用
- `PermissionEnforcer`：按权限判断是否允许执行

当前工具包括基础文件工具、bash、搜索、web-fetch、记忆、TODO、技能、群组通信、MCP 等。

权限不是纯前端显示项，而是后端执行时参与判断。bash 工具还会进行命令风险分级，并可委派到 Docker 沙箱。

**2026-08-09 新增：**
- **并发写防护 CAS**（`tools/file-version.ts`）：read-file 返回附 `[file-version: mtimeMs:size]`，write-file/edit-file 携带可选 `baseVersion` 写前校验，版本不一致拒绝「文件已被其他成员修改，请重新读取」——防多 Agent 静默覆写。
- **安全分类器**（`tools/safety-classifier.ts` + `PermissionMode “auto”`）：auto 模式下 PermissionEnforcer 决策链（deny → allow 排除 bash EXTREME_DANGER → 只读/工作目录内编辑放行 → 其余 needsClassifier），ToolExecutor 调独立 LLM 裁决（reasoning-blind、fail-closed、熔断、allow 缓存），emit `tool:classified` 审计。
- **管家工具分级**：BUTLER_DEFAULT_TOOLS 移除 bash/edit-file/glob/grep（结构约束强制派发），保留 read-file/write-file 供个人事务 md。

## Memory 与 TODO

MemoryStore 同时支持 Markdown 文件和 SQLite/FTS5 搜索，并包含安全扫描、冻结快照、历史记录和信任评分。当前配置只有 `memory` 与 `experience` 两类字符上限。

TODO 系统分为 Global TODO、Agent TODO 和 Group TODO。Agent/Group TODO 支持时间扫描、依赖、完成状态和交付物相关字段；Global TODO 作为 Butler 编排账本，保存 assignee、responsibleAgent、executionRefs、progressSummary、nextAction 和 lastEvent。

**2026-08-09 TODOboard P0 改进**（决策 #3）：TodoItem 新增 `repeat`（daily/weekly/interval + until）/`nextTriggerAt`/`overduePolicy`（re-wake/escalate-to-host + cooldownMinutes/maxRetries）；`getRepeatDueTodos` + `advanceRepeat` 周期推进（超 until 停止）；`getStalePendingTodos` 已触发待完成超冷却低频重唤醒（只重触发不重建，防 300 条刷屏事故）；AgentTodoScanner 补 0time/repeat/condition 触发（`notifyAgentSpoke` 接线到对话完成）。Group→Butler 结构化事件桥：`host-report-event` 工具上报六类事件（blocked/needs_user_decision/completed/failed/scope_change/status_digest）→ 广播 `butler_escalation`；`agent-request-resource` 广播 + 写管家收件箱。

## Market 架构（2026-08-03 新增）

Market 分级机制是「可信能力供应链」的实现层，代码位于 `packages/core/src/market/`：

- **MarketCatalog**：扫描 `data/market/<tier>/<id>/market.json`（tier ∈ official/certified/community），非法或错位 id 跳过；`data/market/installed.json` 原子持久化已安装记录；`buildLocalResources()` 把现有 Agent（排除 butler/host）与技能合成 local 层资源。
- **MarketInstaller**：`buildDependencyTree()` 递归解析依赖（visited 防环，缺失依赖生成 tier=community 保守节点）；`install()` 按拓扑序落盘——skill → `data/skills/<id>/`、agent → `data/agents/<id>/`、group → `data/groups/<id>/`（先装 agent 依赖）——再经 hooks 接线到运行时（Agent 注册 / 群组创建 / 技能重载 / 群组销毁）；社区门禁：树中任一节点 tier=community 且未 `confirmed: true` → `approval_required`；卸载只删自身，依赖不级联（共享资源）。
- **Butler 工具**：`butler-market-recommend`（官方/认证优先、社区 ⚠️ 标注、本地默认路径）与 `butler-market-install`（社区引导 `confirmed: true`）。
- **WS 命令**：`market_list`（含本地聚合与 type/tier/query 过滤）/ `market_get`（详情 + 依赖树）/ `market_install` / `market_uninstall` / `market_installed`，handler 位于 `api/handlers/market.ts`。
- **内置资源**：`packages/core/src/market/bundled/` 是打包源，Runtime 启动时 `initMarketServices()` 首次同步到 `data/market/`（已存在不覆盖），随后 `catalog.reload()`。这与模板文件从 `packages/core/src/templates/` 解析的模式一致。
- **GUI**：扩展页 Market tab（`MarketTab.tsx` + `stores/market.ts` + `ws-handlers/market-handlers.ts`），分层过滤、资源卡片、详情 Sheet（递归依赖树）、社区确认流。
- **hooks 异步约定**：install() 为同步签名，hooks 返回 Promise 时 fire-and-forget（.catch 记日志）。

## Plugin、Skill 与 MCP

### Plugin

插件系统已经具备 manifest、loader、hook、prompt layer、UI extension 等基础结构。Provider 和 Channel 的扩展主要通过插件数据目录接入。

需要注意：部分 plugin hook/prompt layer/tool loading 仍需要进一步验证，尤其是旧全局变量迁移后的兼容性。

### Skill

技能系统基于 `SKILL.md`。前端扩展页可以浏览、搜索、创建和切换技能白名单。技能更适合看作 Agent 的工作方法扩展，而不是传统 App 插件。

### MCP

MCP 基础设施包括 client、manager、stdio/http transport 和 bridge tool。前端扩展页可以管理 MCP 配置。

**2026-08-12 起默认启用 3 个 MCP server**（`claude-code` / `qqbot` / `browser`），runtime 启动时经 `connectAllMCPServers` 自动连接并桥接工具（每个工具以 `mcp:<serverId>:<toolName>` 命名，Agent 经 `mcp-discover`/`mcp-register` 按需注册）。

**StdioTransport env 继承（2026-08-12 修复）**：子进程 env 由 PATH/SystemRoot/TEMP/TMP 白名单改为 `{ ...process.env, ...this.env }`（config env 覆盖）——MCP server 子进程可读取 `.env` 中的凭据（QQ_BOT_APP_ID/QQ_BOT_TOKEN 等）。

**Channel 接线（2026-08-12）**：`registerConfigChannels()`（runtime/channels.ts）从 `config.channels` 构造并注册内建 Channel（当前为 QQBot：enabled 过滤、幂等、enc: 加密凭据解密、env 回退），`startChannels()` 开头调用。`config.channels.qqbot` 启用后，QQ 群 @/私聊消息经 Gateway WebSocket 进入 CoBeing，按 bindTo 路由（当前 bindTo butler），回复经 REST API 送出。

当前应将 MCP 描述为“已具备接入基础设施”，而不是“所有 MCP server 默认可用”——但 `claude-code`、`qqbot`、`browser` 三个已在默认配置中启用。

## GUI 架构

前端是 Tauri 桌面壳中的 React SPA，状态管理以 Zustand 为主。主要视图为：

- ButlerView
- AgentsView
- GroupsView
- DashboardView
- ExtensionsView
- SettingsView

业务通信主要通过 WebSocket 连接本地后端。Tauri 主要提供桌面窗口、托盘、通知、调试等壳能力。

GUI 主题由 `gui-v2/src/stores/theme.ts` 加载 `public/themes/*.json` 并写入 CSS variables。内置主题 manifest 和主题 JSON 使用无缓存请求加载，同 ID 内置主题优先于本地持久化的旧自定义主题，避免发布包主题更新被旧 Sakura Mint 覆盖。聊天气泡通过 `chat.msg-user`、`chat.msg-assistant`、`chat.msg-system`、`chat.msg-tool` token 渲染；当前默认主题是 `sakura-mint`，另有 `executive-workbench` 工作台主题。

用户资料前端状态在 `gui-v2/src/stores/userProfile.ts`，持久化到 `localStorage`。`ChatAvatar` 与 `ChatMessageFrame` 是单聊/群聊共享的消息呈现层，负责头像左右布局、气泡 token 和元信息行。

当前 GUI 的成熟度高于纯 demo，但部分仪表盘指标、高级群组组件、技能执行按钮仍有未完全接入或占位现象。

## 当前架构的主要特点

### 优点

- Agent、Butler、Group 的边界比较清楚。
- 本地优先，天然适合个人数据和长期个性化。
- 文件化 Agent 让用户和高级玩家可以直接理解和修改个体风格。
- 扩展层同时覆盖 Provider、Channel、Skill、Plugin、MCP，有平台化潜力。
- Group 机制已经超出单聊天机器人的范畴，有多智能体协作基础。

### 风险

- 历史能力残留较多，旧文档曾把部分计划能力写成已完成能力。
- 某些模块仍依赖旧式全局变量，和 Runtime 当前 namespace 不完全一致。
- GUI 中有部分组件存在但没有接入主流程，容易造成“看起来有、实际不完整”的体验。
- 普通用户入口仍需要更多产品化包装，否则扩展系统会显得偏工程化。

---

## 架构演进方向

后续最值得优先收敛的是：

1. 把旧全局变量依赖统一迁移到 Runtime namespace 或显式依赖注入。
2. 对插件、MCP、沙箱监控做端到端验证（投票已于 2026-08-09 移除）。
3. Market 分级 v1 已落地（2026-08-03）：继续补充官方认证审核流程、认证远程市场、persona/plugin 资源安装、社区资源版本更新与安全修复机制。
4. 让 Butler 成为普通用户的默认入口，把复杂配置从用户眼前后移。
5. 将 Agent/Group 的高级能力逐步变成可解释、可审查、可回滚的用户体验。

## 2026-08-01 骨架重构（行为不变）

本次为全栈骨架重构，所有功能行为保持不变，仅重组代码边界。重构后各模块职责如下：

### WebSocket 服务层（`packages/core/src/api/`）

- `ws-server.ts` 从 3111 行瘦身到 591 行。`CoreWSServer` 只保留：连接生命周期、心跳/速率限制、命令注册表与 `handler.call(this, ws, msg)` 分发、共享发送原语（`sendToClient`/`broadcast`/`broadcastState`/`logMessage`）。
- 心跳策略（2026-08-05 修复）：pong 超时（20s）仅在心跳 ping（30s 间隔）之后武装，连接建立与客户端消息只清除超时——修复静默客户端（发完消息后等待的测试脚本）在首个 ping 前被误杀的问题。
- 78 个 WS 命令按域拆到 `api/handlers/` 的 14 个模块（system/agent/group/plugin/binding/message/todo/observability/sandbox/skill/enhancement/butler-persona/onboarding/market）。handler 以 `function (this: CoreWSServer, ws, msg)` 形式声明，case 体原样保留（`this.X`/`msg.payload` 不改）。
