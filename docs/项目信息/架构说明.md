# CoBeing 架构说明

> 最后更新：2026-06-11  
> 本文档解释当前代码中的真实架构，不沿用旧版能力清单。

---

## 总体架构

CoBeing 的代码结构可以分为五层：

1. 后端运行时层：负责 Agent、Butler、Group、Tool、Memory、Plugin、MCP、Channel、WebSocket 的启动与编排。
2. 智能体层：Agent、Butler、Group 组成核心 Agent Team 范式。
3. 扩展层：Provider、Channel、Skill、Plugin、MCP 负责外部能力接入。
4. 数据层：`data/` 下保存 Agent、Group、skills、plugins、runtime registry、记忆与工作区。
5. GUI 层：React/Tauri 前端通过本地 WebSocket 调用后端能力。

整体是本地优先架构，用户数据主要保存在本机 `data/` 目录。

SQLite 相关模块采用“优先真实 SQLite，失败降级”的策略：项目当前使用 `better-sqlite3@12.10.0`，可在 Node 24 下加载原生 binding；`memory/SqliteAdapter` 与 `observability/ObservabilityDB` 在 SQLite 不可用时使用同路径 JSON fallback，`group/GroupDB` 与 `group/GroupAgentMemory` 使用内存 fallback。该策略用于避免 Node/native binding 异常时启动失败，但正常路径仍是 SQLite/FTS5。

## 后端包结构

### `packages/core`

核心运行时包，承担系统主体职责。关键模块包括：

- `runtime.ts`：CoBeingRuntime 顶层编排器
- `agent/`：Agent、Butler、AgentRegistry、AgentPaths、ToolAgent
- `group/`：Group、GroupManager、GroupContextV2、WakeSystem、群组记忆
- `conversation/`：会话循环、PromptBuilder、LLM 调用流程
- `tools/`：工具注册、权限执行、沙箱、内置工具
- `memory/`：MemoryStore、SQLite adapter、安全扫描、经验存储
- `todo/`：Agent/Group TODO、扫描器、触发机制
- `api/`：WebSocket server 与 GUI 命令处理
- `mcp/`：MCP client、manager、transport、bridge tool
- `observability/`：运行指标、活动记录、仪表盘数据

### `packages/shared`

跨包共享能力，包括类型定义、事件、日志、文件工具、常量和 master registry。

### `packages/providers`

Provider 接口和 OpenAI-compatible 基类。当前内置代码层主要包含 DeepSeek catalog，更多 Provider 通过 `data/plugins/providers/` 的数据插件扩展。

### `packages/channels`

Channel 接口和 QQ Bot 通道实现。默认配置中 channels 为空，QQ Bot 是可选接入。

### `packages/plugin-sdk`

插件 SDK，包括 manifest 类型、插件加载器、HookBus、PromptLayerRegistry、UIExtensionRegistry。它为 Provider、Channel、UI 扩展和运行时 hook 提供基础设施。

### `packages/mcp-servers`

内置 MCP server 包，目前包含：

- `qqbot`
- `office`

它们是可接入能力，不代表默认启动时自动连接。

## Runtime 启动链路

`CoBeingRuntime` 的职责是把分散的包和数据目录组织成一个可运行系统。

典型启动逻辑包括：

1. 读取配置与环境变量。
2. 初始化 `data/` 目录和 registry。
3. 检查 Docker 沙箱可用性。
4. 加载 Provider 与插件。
5. 初始化 Butler 和默认 Agent。
6. 初始化 GroupManager 并恢复已有 Group。
7. 启动 TODO 扫描器。
8. 启动 MCP manager。
9. 启动 WebSocket server。
10. 启动可选 Channel。

Runtime 是当前系统事实上的“平台内核”。GUI、Butler、Agent、Group、插件和 MCP 都围绕它运行。

## Agent 架构

### Agent 文件系统

每个 Agent 都有自己的目录和核心文件。当前版本的文件职责是：

- `AGENTS.md`：运行规则、工具规则、群组规则、红线
- `CHARACTER.md`：人物形象与表达风格
- `JOB.md`：工作职责和方法论
- `MEMORY.md`：独立会话记忆入口
- `EXPERIENCE.md`：长期经验和用户偏好沉淀
- `config.json`：模型、权限、工具、沙箱、技能白名单

旧版冗余 Agent 文件已经被删除，不能再作为当前架构描述。

### Prompt 构建

PromptBuilder 当前围绕五文件体系工作。它会组合静态规则、项目规则、Agent 人设、角色扮演层、工作职责和动态上下文。

这个设计让“怎么说话”和“怎么工作”分离：

- `CHARACTER.md` 影响表达方式
- `JOB.md` 影响任务处理方式
- `AGENTS.md` 约束边界和工具使用

### 会话循环

Agent 的对话由 ConversationLoop 驱动。它负责构造 prompt、调用 Provider、处理工具调用、写入消息和返回结果。

当前 LLMGateway 虽然存在，但并不是所有 Agent 请求都统一经过它；因此架构描述中应避免把 LLMGateway 写成全局必经链路。

## Butler 架构

Butler 是特殊 Agent，位于用户入口层。

它的核心职责是：

- 与用户对话
- 管理 Agent
- 管理 Group

代码中 Butler 已注册多种管理工具，例如创建/销毁 Agent、创建/销毁 Group、修改 Agent 文件、绑定工作区、操作 TODO、向群组发送消息等。

这让 Butler 可以把对话体验优化为“像一个人”，而把具体任务转交给专门 Agent 或 Group。

2026-06-10 起，Butler 具备一条后端可追踪任务派发链路：`dispatchButlerTask()` 会把用户意图落成 Global TODO、ButlerTask、执行引用，并在目标侧创建 Agent inbox item 或 Group TODO。Butler 工具层提供 `butler-dispatch-to-agent`、`butler-dispatch-to-group`、`butler-get-work-status`、`butler-cancel-work`、`butler-reply-to-group`，旧 `butler-dispatch-task` 保留为 Agent 派发兼容入口。

这条链路目前解决的是“托管账本和状态同步”，还不等于完整产品体验。Group -> Butler 的结构化事件工具、用户决策回流、前端任务回执数据流仍需要继续完善。

---

## Group 架构

Group 是 CoBeing 的多智能体协作单元。

关键组成包括：

- `GroupManager`：创建、恢复、销毁和查询 Group
- `Group`：群组对象和消息入口
- `GroupContextV2`：群组上下文管理
- `WakeSystem`：@mention 后的事件驱动唤醒
- `GroupDB`：群组消息与状态存储
- 群组工作区：最小工作区策略（GUIDE.md + EXPERIENCE.md 自动创建，其余按需生成）
- 群组记忆：Agent 在群组中的上下文和经验

Group 的核心交互机制是：用户或 Agent 向群组发送消息，消息中的 @mention 会进入唤醒队列，被唤醒成员读取上下文并回复。

**协作策略**（2026-06-09）：采用纯 prompt 驱动，不依赖重协议状态机。规则分布在四个层级：
1. `GUIDE.md` — 群组规则模板（场景定义、审批点、资源申请链、禁止行为）
2. `HOST_JOB.md` — 群主职责模板（9 项核心职责、触发时机、判断框架），位于 `templates/host/`
3. Agent 群组上下文 — 6 步判断框架注入到 `buildGroupCollaborationContext()`
4. `group-send` 工具描述 — 非阻塞协作旁路消息

## ToolAgent 架构

ToolAgent 是后台临时工作单元。它与普通 Agent 不同：不进入 AgentRegistry，不出现在普通 Agent 列表，不拥有长期人格和长期任务责任。

当前代码中 ToolAgent 相关文件集中在 `packages/core/src/agent/tool-agent/`：

- `base.ts`：独立 LLM 工具循环和 `data/toolagents/<type>/` 配置读取。
- `types.ts`：ToolAgent 类型、运行配置、结果类型和 `ToolAgentSpec`。
- `spec.ts`：统一配置卡 loader，合并数据目录中的 config/prompt 与默认策略。
- `creator.ts`：Creator ToolAgent，支持 Agent 核心文件生成和 Group 创建草案。
- `memory.ts`：Memory ToolAgent，返回经验条目、`MEMORY.md` 修改建议和风险警告。
- `review.ts`、`judgment.ts`、`clone.ts` 以及能力/成长/归档相关 ToolAgent。

`ToolAgentSpec` 记录触发来源、可见性、写入策略和失败策略。默认边界是：ToolAgent 返回结构化结果，由调用方应用；能写入长期文件的场景也必须由调用方决定，不让 ToolAgent 自己成为长期记忆或资源管理主体。

Group 创建链路已经接入 Creator ToolAgent：WebSocket `create_group` 创建群组后，会生成并写入 `GUIDE.md` / `PLAN.md` 草案，同时把成员缺口、初始任务和用户确认问题交给 host 继续向用户确认。

## Tool 与权限架构

工具系统由三部分组成：

- `ToolRegistry`：注册工具定义
- `ToolExecutor`：执行工具调用
- `PermissionEnforcer`：按权限判断是否允许执行

当前工具包括基础文件工具、bash、搜索、web-fetch、记忆、TODO、技能、群组通信、MCP 等。

权限不是纯前端显示项，而是后端执行时参与判断。bash 工具还会进行命令风险分级，并可委派到 Docker 沙箱。

## Memory 与 TODO

MemoryStore 同时支持 Markdown 文件和 SQLite/FTS5 搜索，并包含安全扫描、冻结快照、历史记录和信任评分。当前配置只有 `memory` 与 `experience` 两类字符上限。

TODO 系统分为 Global TODO、Agent TODO 和 Group TODO。Agent/Group TODO 支持时间扫描、依赖、完成状态和交付物相关字段；Global TODO 作为 Butler 编排账本，保存 assignee、responsibleAgent、executionRefs、progressSummary、nextAction 和 lastEvent。

当前它已经能承载“提醒、任务跟踪、协作推进”的基础逻辑，并能在 Butler tracked dispatch、Agent task report/complete、Group TODO complete 三条路径上同步全局账本。但它仍不应被夸大为完全自动的复杂工作流引擎：资源审批、结构化跨层事件、失败恢复和用户决策路由还需要继续补齐。

## Plugin、Skill 与 MCP

### Plugin

插件系统已经具备 manifest、loader、hook、prompt layer、UI extension 等基础结构。Provider 和 Channel 的扩展主要通过插件数据目录接入。

需要注意：部分 plugin hook/prompt layer/tool loading 仍需要进一步验证，尤其是旧全局变量迁移后的兼容性。

### Skill

技能系统基于 `SKILL.md`。前端扩展页可以浏览、搜索、创建和切换技能白名单。技能更适合看作 Agent 的工作方法扩展，而不是传统 App 插件。

### MCP

MCP 基础设施包括 client、manager、stdio/http transport 和 bridge tool。前端扩展页可以管理 MCP 配置。默认配置不自动连接 MCP server。

当前应将 MCP 描述为“已具备接入基础设施”，而不是“所有 MCP server 默认可用”。

## GUI 架构

前端是 Tauri 桌面壳中的 React SPA，状态管理以 Zustand 为主。主要视图为：

- ButlerView
- AgentsView
- GroupsView
- DashboardView
- ExtensionsView
- SettingsView

业务通信主要通过 WebSocket 连接本地后端。Tauri 主要提供桌面窗口、托盘、通知、调试等壳能力。

GUI 主题由 `gui-v2/src/stores/theme.ts` 加载 `public/themes/*.json` 并写入 CSS variables。内置主题 manifest 和主题 JSON 使用无缓存请求加载，同 ID 内置主题优先于本地持久化的旧自定义主题，避免发布包主题更新被旧 Sakura Mint 覆盖。聊天气泡通过 `chat.msg-user`、`chat.msg-assistant`、`chat.msg-system`、`chat.msg-tool` token 渲染；当前默认主题是 `sakura-mint`，另有 `executive-workbench` 工作台主题。

用户资料前端状态在 `gui-v2/src/stores/userProfile.ts`，持久化到 `localStorage`。`ChatAvatar` 与 `ChatMessageFrame` 是单聊/群聊共享的消息呈现层，负责头像左右布局、气泡 token 和元信息行。

当前 GUI 的成熟度高于纯 demo，但部分仪表盘指标、高级群组组件、技能执行按钮仍有未完全接入或占位现象。

## 当前架构的主要特点

### 优点

- Agent、Butler、Group 的边界比较清楚。
- 本地优先，天然适合个人数据和长期个性化。
- 文件化 Agent 让用户和高级玩家可以直接理解和修改个体风格。
- 扩展层同时覆盖 Provider、Channel、Skill、Plugin、MCP，有平台化潜力。
- Group 机制已经超出单聊天机器人的范畴，有多智能体协作基础。

### 风险

- 历史能力残留较多，旧文档曾把部分计划能力写成已完成能力。
- 某些模块仍依赖旧式全局变量，和 Runtime 当前 namespace 不完全一致。
- GUI 中有部分组件存在但没有接入主流程，容易造成“看起来有、实际不完整”的体验。
- 普通用户入口仍需要更多产品化包装，否则扩展系统会显得偏工程化。

---

## 架构演进方向

后续最值得优先收敛的是：

1. 把旧全局变量依赖统一迁移到 Runtime namespace 或显式依赖注入。
2. 对插件、MCP、投票、沙箱监控做端到端验证。
3. 把 Market 分级和官方认证机制产品化，而不是只保留扩展目录。
4. 让 Butler 成为普通用户的默认入口，把复杂配置从用户眼前后移。
5. 将 Agent/Group 的高级能力逐步变成可解释、可审查、可回滚的用户体验。

## 2026-06-12 GUI Surface Architecture

前端新增共享布局层：
- `gui-v2/src/components/layout/Surface.tsx`
  - `SurfaceCard`: 统一主要卡片的背景、边框、圆角、内边距和主题阴影。
  - `WorkbenchLayout`: 统一主体工作区的网格结构，支持左侧列表卡片、标题卡片和主体内容/对话卡片。

当前页面层级规则：
- `TitleBar` 属于应用外壳顶部条，不纳入主体卡片系统。
- `NavBar` 属于最左侧固定导航栏，不等同于主体左侧列表卡片。
- `MainContent` 根据视图将聊天、设置、仪表盘、扩展页面接入 `WorkbenchLayout`。
- `Sidebar` 在主体区域内渲染左侧列表卡片；管家视图改由 `GlobalTodoPanel` 承担左侧列表卡片。
- `GlobalTodoPanel` 使用真实 `GlobalTodoInfo` 字段渲染管家全局任务，并通过显示模型测试与核心界面审计防止 JSX literal unicode escape 回归。
- `ChatView` 和 `GroupChatView` 使用同一套标题卡片 + 对话卡片结构；对话卡片内部再分消息区和输入区。
- `Sheet` / `Dialog` 是设置、详情、新建和确认等浮层的基础设施，统一使用主题化磨砂遮罩与 `--shadow-surface-lg`。
