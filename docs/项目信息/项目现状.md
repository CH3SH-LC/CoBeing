# CoBeing 项目现状

> 最后更新：2026-06-12  
> 依据：代码库、`config/default.json`、`PROGRESS.md`、前后端实现扫描与子智能体审计结论。

---

## 一句话现状

CoBeing 当前是一个本地优先的多智能体桌面系统：用户可以通过管家、独立 Agent、群组、扩展页与运行时交互。代码中已经形成 Agent Team 的基本架构，但部分高级能力仍处于“有接口/有工具/有数据结构，但默认链路未完全打通”的阶段。

本文档只描述代码中能看到的事实，不把战略设想、历史计划或未接入能力写成已完成能力。

## 已经落地的核心能力

### 1. Runtime 与系统编排

`CoBeingRuntime` 是后端顶层编排器，负责启动 Provider、插件、Butler、Agent、Group、MCP、WebSocket、Channel 与 TODO 扫描器。它是当前项目的真实后端中枢。

启动过程中会读取默认配置、初始化数据目录、加载 Provider 与插件、恢复注册表中的 Agent/Group，并在 GUI 开启时启动本地 WebSocket 服务。

当前 `better-sqlite3` 已升级到 `12.10.0`，在 Node 24.13.0 下可生成并加载 `better_sqlite3.node`；Memory/Group/Observability 默认走真实 SQLite/FTS5 路径。在开发环境缺少 native binding 时，这些入口仍会降级到 JSON 文件或内存存储，避免 Runtime 启动失败。

### 2. Agent

Agent 已经具备独立文件系统、配置、记忆、工具注册、会话循环、Provider fallback、并发保护和生命周期管理。

当前 Agent 核心文件已经从旧版多文件结构收敛为（2026-08-05 起执行型智能体抛弃角色）：

- `AGENTS.md`：启动规则、工具规则、协作规则、行为边界
- `EXPRESSION.md`：人味表达规范（篇幅/句式/禁语/真人信号/群聊纪律，**无身份设定**）——2026-08-05 起取代 CHARACTER.md，执行型智能体不再有独立角色
- `JOB.md`：工作职责、思考方式、执行流程、输出规范
- `MEMORY.md`：独立工作时的事件记忆入口
- `EXPERIENCE.md`：长期经验、用户偏好、工具心得、教训沉淀
- `config.json`：模型、权限、工具、沙箱、技能白名单等运行配置

Prompt 构建链路关键顺序为：静态层、`AGENTS.md`、表达/人格层（**优先 EXPRESSION.md；历史 Agent 无 EXPRESSION 时兼容 CHARACTER.md + 角色扮演强化指令，管家 Butler 因保留 CHARACTER 走兼容路径**）、`JOB.md`、动态上下文。

管家（Butler）与群主（Host）特殊：管家保留 `CHARACTER.md` 人格（4 人格模板），群主无角色、遵循 EXPRESSION.md（ensureHostDir 首次创建时复制）。

### 3. Butler 管家

Butler 是一个特殊 Agent，定位不是直接完成所有具体工作，而是作为用户入口、Agent 管理者和 Group 管理者。

代码中 Butler 已经拥有创建/销毁 Agent、创建/销毁 Group、列出资源、修改 Agent 文件、绑定工作区、管理 TODO、向群组发送消息、切换自身人格（2026-08-05 新增 `butler-list-personas` / `butler-set-persona` / `butler-update-style`，对话中按用户喜好调整管家形象与称呼）等工具。

2026-08-05 管家 JOB.md 重写为「多步任务推进流程」（澄清 → 推进 → 确认点 → 继续）：需求模糊先澄清 2-3 个关键问题；方案出稿/主观偏好/群组需决策时**必须停下向用户确认**（等待期间任务置 waiting_user 状态）；确认后继续推进。新增「首启对话」范式：对话式收集用户信息与对管家的喜好。

这和产品战略中的“管家不做所有具体工作，而是负责对话、管理智能体、管理群组”基本一致。

截至 2026-06-10，Butler 的任务托管后端链路已补齐第一闭环：`Runtime` 挂载 `GlobalTodoStore`、`ButlerTaskStore`、`GroupButlerBindingStore`；Butler 派发到 Agent/Group 会创建 Global TODO、ButlerTask 和对应 Agent inbox / Group TODO，并写入 executionRefs；Agent accept/report/complete 会同步 Global TODO 与 ButlerTask 状态；WS `find_agent` / `dispatch_task` 不再只是占位。

仍需谨慎表述的是：Group -> Butler 的结构化 Host 事件工具、资源请求审批队列还没有完整产品化。前端任务回执真实数据流已于 2026-08-04 打通（回执卡片渲染 + 状态流转刷新 + 群组派发回执展示）。

### 4. Group 群组

Group 是当前多智能体协作的主要组织单元，已经具备：

- GroupManager 管理生命周期
- GroupContextV2 管理群组上下文
- WakeSystem 处理 @mention 唤醒队列
- 群组工作区文件（2026-06-09 精简为 GUIDE.md + EXPERIENCE.md 自动创建，其余按需生成）
- 群组数据库
- 群组 TODO
- 成员模型切换
- Agent 群组记忆
- 通过 `postMessage()` / `group-send` 触发成员响应
- 用户参与：成员在群组内 `@用户`（@用户/@主人/@老板/@user）会触发前端用户唤醒（通知+未读，parseMentions 支持 2 字符别名）；用户消息经 send_message `[群组 gid]` 前缀进入群组（fromAgentId="user"）触发成员响应

`GroupDB` 与 `GroupAgentMemory` 默认使用 `better-sqlite3` 持久化群组消息和群组记忆；SQLite native binding 不可用时才使用进程内内存 fallback，保证群组创建、消息同步和唤醒链路不会被原生模块缺失阻断。

**协作方式**（2026-06-09 更新）：从模块化工作流（PLAN.md + TODOboard 阶段驱动）升级为**纯 prompt 驱动 + 轻结构承载**。协作规则分布在四个层级：HOST_JOB.md（群主 9 项职责 + 判断框架）、GUIDE.md（群组规则 + 审批点 + 资源链）、Agent 群组上下文（6 步判断框架）、`group-send` 工具描述（非阻塞协作旁路）。

需要注意：Agent 在群组内写入最终回复时，使用的静默追加不一定会再次触发新的 @mention 链路。真正触发唤醒的主要入口是 `Group.postMessage()` 或显式群组工具。

### 5. GUI

前端是 React 19 + Tauri 2 的桌面 SPA。当前固定六个主入口：

- 管家
- 智能体
- 群组
- 仪表盘
- 扩展
- 设置

用户可以在 GUI 中和 Butler/Agent/Group 对话，创建 Agent，创建 Group，修改 Agent 配置，查看 TODO，管理技能/MCP/插件，设置 Provider、Channel、Sandbox，并查看部分仪表盘信息。

2026-06-11 已修复管家页导航渲染错误：`Sidebar` 现在先完成所有 hooks，再按 `activeView` 渲染管家全局任务栏或 Agent/Group 侧栏，避免从管家页切换到其他页面时触发 React hook 顺序错误。

2026-06-11 已按 A 方案将 GUI 默认视觉方向调整为樱花薄荷，B 方案工作台配色作为 `executive-workbench` 内置主题保留。2026-06-12 默认樱花薄荷主题进一步增强为浅樱粉/薄荷渐变基底、奶白半透明面板和更明显的樱花糖粉/薄荷糖绿气泡。主题系统要求 `chat.msg-user`、`chat.msg-assistant`、`chat.msg-system`、`chat.msg-tool`，真实单聊和群聊气泡会随主题 token 变化。

设置页新增“个人资料”：用户可以设置昵称、首字/Emoji/图片头像；真实单聊和群聊中，用户消息显示昵称和右侧头像，智能体消息显示左侧头像。Agent 详情中的能力、任务、成长 tabs 也已做主题 token 与卡片化视觉整理。

2026-08-04 GUI 清理轮：Agent 详情新增「时间线」tab（工具调用成功/失败时间线）、群组详情新增「健康」tab（任务完成率/成员活跃度/最长阻塞）、设置页新增「唤醒队列」（运维组）；管家任务回执真实数据流完整打通——单聊/群组会话中的回执卡片随状态流转实时刷新（running → waiting_user/completed/failed），管家派发给群组的任务在群组会话展示回执；技能执行、沙箱真实指标、通知音效均接入真实链路（见「部分实现或需要谨慎表述的能力」）。

### 6. 工具与权限

后端已经有 ToolRegistry、ToolExecutor、PermissionEnforcer 与多级权限体系。内置工具包括 bash、文件读写、代码编辑、glob、grep、web-fetch，以及记忆、TODO、技能、群组通信、MCP 等扩展工具。

bash 工具支持沙箱委派：如果 Docker 沙箱启用且可用，会优先走沙箱执行；如果 Docker 不可用，运行时会检测并降级。

### 7. 记忆与经验

MemoryStore 已实现 Markdown 存储、SQLite/FTS5 检索、冻结快照、历史记录、信任评分与安全扫描。当前配置中的字符上限只有：

- `memory`: 3000
- `experience`: 5000

历史文档中提到的 `user/tools` 四目标存储已经不是当前配置事实。Memory ToolAgent 当前输出协议已对齐为 `entries + memoryUpdates + warnings`：经验条目用于 `EXPERIENCE.md`，`MEMORY.md` 修改只作为建议返回，由调用方决定是否应用。

当前 `SqliteAdapter` 默认使用 `better-sqlite3` + FTS5；在 SQLite/FTS5 不可用时会写入同路径 `.fallback.json`，保障记忆条目、历史、搜索、信任反馈和同步状态在缺少 native binding 的开发环境中仍可用。

### 8. ToolAgent 工具智能体

ToolAgent 是当前代码中的临时后台工作单元，不进入普通 Agent 列表，也不承担长期人格、关系或任务托管。已有类型包括 review、judgment、clone、memory、creator、growth-reviewer、task-archive、capability-updater。

截至 2026-06-10，代码中已新增 `ToolAgentSpec` 与 `loadToolAgentSpec()`，可以从 `data/toolagents/<type>/config.json` 和 `prompt.md` 读取统一配置卡，包含触发说明、可见性策略、写入策略和失败策略。

Creator ToolAgent 已纳入类型体系：创建 Agent 时仍用于生成 `CHARACTER.md` / `JOB.md`；创建 Group 时会生成 `GUIDE.md`、`PLAN.md`、成员缺口、初始任务和需要向用户确认的问题。`create_group` 会应用低风险文件草案，并把建议交给 host 首条系统消息，不会静默创建额外 Agent 或安装资源。

需要谨慎表述的是：ToolAgent 的前端可见性和日志区分目前主要是协议字段和后台日志层面的基础，尚未形成完整 GUI 观测面板或统一评估机制。

### 9. TODO 自动化

Agent 与 Group 都有 TODO 存储和扫描机制，支持时间触发、0time、依赖、完成回调、状态变更等结构。当前更可靠的判断是：TODO 系统已经存在并可用，但复杂条件触发的语义主要依赖 Agent/工具侧处理，不应宣传为完全自动的条件推理调度系统。

截至 2026-06-08，群组 TODO 的完成路径进一步收紧：前端 WS、Host 管理工具、TODO 批量完成和验收通过在群组级场景下会优先走 `GroupTodoScanner.complete()`，从而保留依赖满足后的下游 @mention 通知、onComplete 动作链和工作区进度同步。`condition` 与 `0time` TODO 也增加了已触发待完成项的重复触发防护。

2026-08-05 修复 0time 语义：已触发的 0time TODO 保持 pending 直到被完成，**不再"过期重建"**（旧逻辑每次扫描 expired+新建同内容条目，单任务数小时堆积 300+ 重复条目并每 2 分钟刷屏群组上下文）；对长期未完成（>10 分钟）的 0time TODO 低频重新触发一次，防止任务被遗忘且不刷屏。群组 TODO 的 0time 触发消息只会出现一次（除非超时重触发）。

TODO 变更 WebSocket 事件现在应携带 `scope`、`agentId`、`groupId` 等上下文，前端 TODO 面板可以按当前 Agent/Group 范围决定是否刷新。

截至 2026-06-10，Global TODO 已从“手动账本”向自动任务流推进了一步：Butler tracked dispatch 会自动创建 Global TODO 和执行引用；Agent task inbox 的状态会通过 `mapAgentStatusToGlobal()` 映射回全局状态；Group TODO 完成会按具体 executionRef.todoIds 精确更新对应 Global TODO，避免同一 Group 上多个全局任务被误更新。

### 10. 插件、技能、MCP

项目已经有 plugin-sdk、插件加载器、HookBus、PromptLayerRegistry、UIExtensionRegistry、SkillRepository、MCP client/manager/transport/bridge tool，以及 QQBot/Office MCP server 包。

默认配置中 MCP server 为空，插件与 MCP 能力更适合被描述为“已经有扩展基础设施与部分可配置入口”，而不是“所有扩展链路已默认打通”。

### 11b. 管家入口产品化（2026-08-04 四阶段完成）

- **任务转接真实化**：`butler_task_updated` 广播携带结构化视图（ButlerTaskReceiptPayload）；前端回执卡片（TaskReceiptCard）首次真实点亮、butlerTasks store 复活（GlobalTodoPanel 管家任务小计）；ChatInputActions 派发菜单结构化 dispatch_task（支持 agent/group 目标）；管家 JOB.md 分级转接规则（寒暄/问答/短润色自己答，复杂/协作/长期任务默认派发，不确定先问用户）。

- **低打扰提示**：Market 推荐纪律写入 JOB.md（官方且明显优于本地才轻量提示 ≤1 次/会话、社区必须确认、本地已有能力时闭嘴）。

### 11. Market 分级机制（2026-08-03 落地 v1）

Market 分级机制已从战略落地为代码：

- **四层信任分级**：官方内置（official，随应用打包）、官方认证（certified，预留层）、社区（community，强制用户确认）、本地私有（local，现有 Agent/技能自动聚合展示）。代码位置：`packages/core/src/market/`。
- **依赖树透明**：group → agent → skill 依赖树安装前完整返回（`market_get` / 安装结果），缺失依赖生成 community 保守节点，防环保护；GUI 详情浮层递归渲染。
- **社区门禁双层执行**：安装器层（无 `confirmed: true` 返回 `approval_required`）与 GUI 确认流层（警告区 + 依赖树 + 确认安装按钮）。
- **管家推荐**：Butler 新增 `butler-market-recommend`（官方/认证优先、社区 ⚠️ 标注）与 `butler-market-install`（社区引导确认）。
- **WS 命令**：`market_list` / `market_get` / `market_install` / `market_uninstall` / `market_installed`。
- **GUI 入口**：扩展页新增 Market tab（分层过滤、资源卡片、详情浮层、安装/卸载）。
- **内置示例资源**：3 个官方（旅行规划 skill、旅行规划师 agent、旅行规划小队 group，构成完整依赖链）+ 1 个社区（记账小助手，演示门禁），首次启动从 `packages/core/src/market/bundled/` 同步到 `data/market/`。
- **数据布局**：`data/market/<tier>/<id>/market.json`（清单）+ 载荷文件；`data/market/installed.json` 记录已安装条目。
- **边界**：persona 与 plugin 资源暂未进入安装链路；官方认证的审核流程、认证远程市场、社区资源版本更新机制仍未落地。

## 部分实现或需要谨慎表述的能力

### Provider

旧版 README 曾把多个 Provider 写成默认原生能力，这个说法不准确。

当前代码事实是：

- 默认配置只启用 `deepseek`
- `packages/providers` 中主要是 Provider 接口、全局注册表、OpenAI-compatible 基类和 DeepSeek catalog
- `data/plugins/providers/` 中存在 deepseek、zhipu、qwen、minimax、volcengine、moonshot、mimo、custom 等数据插件

因此更准确的表述是：内置 DeepSeek / OpenAI-compatible Provider 基础，其他 Provider 主要通过数据插件扩展。

### 插件系统

插件系统已具备 Provider、Channel、UI Extension、HookBus、PromptLayer 的基础结构。但工具插件加载时机、memory backend 插件、hook/prompt layer 与旧全局变量的兼容性仍需继续验证。

### MCP

MCP client、manager、stdio/http transport、bridge tool 都存在；QQBot 与 Office MCP server 包也存在。但默认 `mcpServers` 为空，且部分 discover/register 逻辑仍依赖旧式全局变量，和 Runtime 当前 namespace 不完全一致。

更安全的说法是：MCP 基础设施存在，前端可以配置 MCP，但完整 discover/register 热接入链路仍需专项验证。

### 投票与仲裁

VoteStore 和投票工具存在，但工具注册依赖的旧全局变量与 Runtime 当前设置并不完全一致。投票可以作为底层能力或计划能力描述，不能写成 GUI 完整可用的成熟协作闭环。

### LLM Gateway

LLMGateway 实现了队列、RPM、重试等逻辑，但 ConversationLoop 当前主要直接调用 Provider。不能说所有 Agent 请求都已经统一经过 LLMGateway。

### 沙箱

DockerSandbox、ContainerPool、bash 委派、运行时检测已经存在。网络白名单和资源隔离需要按实际 Docker 环境验证；前端沙箱监控中的部分 CPU/内存/磁盘指标存在占位现象。

### 前端高级组件

## 当前产品形态判断

CoBeing 当前更接近“个人 AI Agent Team 桌面系统”的工程原型，而不是企业工作流平台。

它已经具备普通用户入口需要的基础结构：

- 用户可以只面对 Butler
- 进阶用户可以进入 Agent 或 Group 直接操作
- Agent 可个性化
- Group 可承载复杂协作
- Extension 页面可承接 skills、plugins、MCP

但它还没有完全形成真正面向普通用户的低摩擦产品：

- Market 已形成官方/社区/本地分级安装体验（2026-08-03 v1：扩展页 Market tab + 依赖树 + 社区确认门禁 + 管家推荐工具），但官方认证审核流程、认证远程市场与社区资源版本更新机制仍未落地
- 管家推荐已具备工具 + 纪律规则（2026-08-04 JOB.md 低打扰纪律），但推荐评分与阈值策略尚未产品化（以 prompt 纪律为主）
- 初次使用引导已从告知型教程升级为兴趣问卷 + 初始 Agent 生成（2026-08-04 OnboardingOverlay），问卷结果与 Agent 质量需真实用户验证
- “超级个体”的体验需要更多生活场景闭环来证明价值
