# CoBeing 核心技术

> 最后更新：2026-08-09  
> 本文档说明 CoBeing 的核心技术主张：三层智能体、TODOboard、群组驱动的多智能体协作。它介于 `产品战略.md` 和 `架构说明.md` 之间，强调“为什么这套架构值得存在”以及“下一步应该往哪里强化”。

---

## 一句话技术定位

CoBeing 的核心技术不是单个聊天机器人，也不是传统工作流系统，而是一个面向个人用户的 Agent Team 运行架构。

它的关键假设是：普通用户真正需要的不是“一个万能 AI”，而是一个可以被管家组织起来的小型智能体团队。管家负责理解用户和调度资源，群组负责承载复杂协作，通用智能体负责长期任务角色，工具智能体负责可复用的专业能力，TODOboard 负责把任务状态变成系统可理解、可触发、可沉淀的协作对象。

---

## 技术主轴

CoBeing 可以概括为四条技术主轴：

- 三层智能体：核心智能体、通用智能体、工具智能体。
- 群组驱动：以 Group 作为多智能体协作的长期任务空间。
- TODOboard：以任务板统一任务状态、触发条件、依赖关系和交付验收。
- 本地个性化：以文件化 Agent、记忆、经验和扩展机制承载个人风格。

其中最重要的是群组驱动。没有群组，系统只是多个 Agent 的集合；有了群组，Agent 才能围绕同一个目标、上下文和进度进行持续协作。

---

## 三层智能体设计

### 第一层：核心智能体

核心智能体是系统级角色，不只是普通 Agent。当前最重要的是管家和群主。

#### 管家 Butler

管家是用户默认入口，职责应该收敛为三件事：

- 和用户对话。
- 管理智能体。
- 管理群组。

管家的技术价值在于把复杂系统折叠成自然语言界面。用户不需要知道什么时候该创建 Agent、什么时候该创建 Group、什么时候该安装 Skill 或 Plugin，这些判断可以先交给管家完成。

管家不应该被设计成“万能执行者”。如果管家什么都做，它会变成又一个聊天助手；如果管家主要做理解、关系、调度和解释，它就能成为个人 AI 系统的入口层。

#### 群主 Host

群主是群组内的核心智能体，负责把用户目标转化为可协作的群组过程。

它的职责包括：

- 理解群组目标。
- 拆解任务。
- 分配或建议成员分工。
- 跟踪进度。
- 发现阻塞。
- 组织讨论。
- 汇总结论。
- 推动验收与复盘。

管家面向用户，群主面向群组。两者都属于核心智能体，但工作场景不同：管家负责跨 Agent/Group 的入口管理，群主负责单个 Group 内的协作秩序。

### 第二层：通用智能体

通用智能体是用户可以长期拥有和定制的工作个体。

它们通常具备：

- 独立职责（无独立角色/人设——2026-08-05 起执行型智能体抛弃 CHARACTER）。
- 独立模型配置。
- 独立工具白名单。
- 独立记忆与经验。
- 可编辑的 `EXPRESSION.md`（人味表达规范：怎么说）和 `JOB.md`（怎么做）。

通用智能体适合承担持续存在的个人角色，例如旅行规划师、写作伙伴、学习教练、研究员、代码审查员、家庭事务助理。

它们不是一次性函数，而是可以随着用户互动积累风格、偏好、经验和判断标准的长期队友。**人味分级**：管家（Butler）保留人格形象（CHARACTER.md，4 人格模板），是与用户直接对话的人味入口；执行型智能体没有身份设定，但在群组内回复遵循「人味表达规范」（短句、第一人称、结论先行、不客服腔、不确定就说出来）——像真人同事说话，但不扮演任何角色。

### 第三层：工具智能体

工具智能体是更窄、更专业、更可复用的能力单元。

它们和通用智能体不同，不强调人格、关系和长期陪伴，而强调稳定完成某类子任务。例如：

- 审查。
- 判断。
- 克隆。
- 记忆提取。
- 结构化转换。
- 专门检索。
- 专门生成。

工具智能体的技术价值在于把复杂能力从普通 Agent 中拆出去，让系统形成“角色智能体 + 专业工具智能体”的组合结构。

这样可以避免每个 Agent 都无限膨胀，也让能力复用更清晰：通用智能体负责场景理解和任务推进，工具智能体负责可重复的专业动作。

截至 2026-06-10，ToolAgent 已有第一步标准化实现：`ToolAgentSpec` 统一描述触发方式、可见性、写入策略和失败策略；`creator` 已纳入 ToolAgent 类型，并可辅助创建 Agent 与 Group；Memory ToolAgent 能返回 `EXPERIENCE.md` 经验条目和 `MEMORY.md` 修改建议。它们仍保持“返回结果、调用方应用”的边界，不直接获得长期资源管理权。

## 三层之间的协作关系

理想调用链路不是线性的，而是分层调度：

```text
用户
  ↓
管家 Butler
  ↓
创建/选择 Agent 或 Group
  ↓
群主 Host 组织群组协作
  ↓
通用智能体承担角色任务
  ↓
工具智能体完成专业子动作
  ↓
结果回到群组、管家或用户
```

这套结构的关键不是层级权力，而是职责隔离。

- 管家不陷入具体执行细节。
- 群主不替代所有成员完成工作。
- 通用智能体不把所有工具能力塞进自身 prompt。
- 工具智能体不承担用户关系和长期上下文。

职责隔离越清楚，系统越容易扩展，也越容易让普通用户理解。

## TODOboard 技术设想

当前项目已经有 Agent TODO、Group TODO、扫描器、时间触发、依赖和状态字段。下一步应把 TODO 从“待办清单”升级为“TODOboard”。

2026-06-08 的实现补强已经把群组 TODO 的部分闭环收紧：群组级完成入口统一优先经过 `GroupTodoScanner.complete()`，使依赖满足后的下游唤醒、onComplete 动作链和工作区进度记录不再只存在于 Agent 工具路径里；TODO WebSocket 事件也补充了 scope 上下文，便于前端按 Agent/Group 范围同步任务面板。

**2026-08-09 决策 #3 P0 改进已落地**：TodoItem 新增 `repeat`（daily/weekly/interval + until）、`nextTriggerAt`、`overduePolicy`（re-wake/escalate-to-host + cooldownMinutes/maxRetries）。触发引擎补齐三环——`getRepeatDueTodos` + `advanceRepeat`（周期推进、超 until 停止）、`getStalePendingTodos`（已触发待完成超冷却低频重唤醒，只重触发不重建）、AgentTodoScanner 补 0time/repeat/condition（`notifyAgentSpoke` 接线到对话完成）。这让 TODO 从"提醒清单"进一步成为**系统可跨时间自动推进的任务协议**（goal 机制补齐核心一环）。P1 完整协议（统一 TriggerEngine/升级阶梯/cron 追赶）仍可后续。

TODOboard 不是简单 UI 看板，而是多智能体协作的任务状态协议。

### TODOboard 的核心对象

一个任务不应只包含标题和完成状态，还应包含：

- 目标：为什么做这件事。
- 所属空间：属于哪个 Agent、Group 或用户上下文。
- 负责人：哪个 Agent 或用户负责推进。
- 参与者：哪些 Agent 需要协作。
- 状态：未开始、进行中、阻塞、待审查、返工、完成。
- 依赖：前置任务和后续任务。
- 触发器：时间、事件、条件、外部消息。
- 交付物：文件、消息、链接、结构化结果。
- 验收标准：什么算完成。
- 复盘记录：做完后沉淀了什么经验。

当 TODO 具备这些字段，它就不再只是提醒，而是系统能理解的任务节点。

### TODOboard 的四个作用

#### 1. 协作可视化

用户和管家可以看到任务处于哪里、谁在负责、哪里阻塞、下一步是什么。

这对普通用户尤其重要。多智能体系统如果没有可视化状态，会很快变成“我不知道 AI 在干什么”的黑箱。

#### 2. 调度协议

群主可以根据 TODOboard 判断应该唤醒谁、催促谁、等待谁、向用户请求什么信息。

任务状态成为 Agent 间协作的共享协议，而不是散落在聊天记录里的自然语言描述。

#### 3. 触发器系统

TODOboard 可以成为系统主动性的来源。

例如：

- 到时间提醒用户。
- 上游完成后唤醒下游 Agent。
- 某任务阻塞超过阈值后通知群主。
- 用户回复某个条件后继续推进。
- 外部 Channel 或 MCP 事件触发任务更新。

主动性如果只靠 Agent 自己“记得”，会不稳定；如果由 TODOboard 管理，就更容易审查、暂停、回滚和解释。

#### 4. 经验沉淀入口

任务完成后，系统可以基于 TODOboard 复盘：

- 哪个拆解有效。
- 哪个 Agent 适合这类任务。
- 哪些工具调用有用。
- 哪些阻塞反复出现。
- 用户偏好是什么。

这样经验不是从聊天里模糊提取，而是围绕明确任务节点沉淀。

## 群组驱动的多智能体合作技术

群组是 CoBeing 最关键的技术单元。它不应该只是“多人聊天室”，而应该是一个长期存在的任务空间。

### 1. 群组作为任务空间

一个 Group 应该包含：

- 目标。
- 成员。
- 角色。
- 消息上下文。
- 工作区文件。
- TODOboard。
- 进度状态。
- 决策记录。
- 经验沉淀。

这意味着群组不是一次性会话，而是一个可以持续推进任务的工作容器。

普通聊天的单位是 message；CoBeing 群组的单位应该是 project-like context。

### 2. 群组作为上下文容器

多智能体协作最难的问题之一是上下文污染。

如果所有 Agent 共享同一段完整聊天记录，会出现：

- 信息过载。
- 角色边界模糊。
- 无关内容干扰。
- Agent 不知道自己应该响应什么。
- 群组长期运行后上下文不可控。

群组上下文应该分层：

- 群组公共上下文：目标、计划、当前进度、关键决策。
- 成员私有上下文：某个 Agent 自己负责的任务、私有推理和草稿。
- 任务上下文：与某个 TODO 相关的局部材料。
- 历史摘要：长期消息压缩后的结构化记录。

当前代码中已经存在 GroupContextV2、WakeSystem、群组工作区和群组记忆，这是群组上下文容器的工程基础。

### 3. 群组作为唤醒系统

多智能体协作不应该让所有 Agent 对每条消息都响应。

更合理的机制是事件驱动唤醒：

```text
消息进入群组
  ↓
识别 @mention / 任务触发 / 状态变化
  ↓
相关 Agent 进入唤醒队列
  ↓
Agent 读取裁剪后的上下文
  ↓
Agent 回复、更新任务或调用工具
  ↓
群组状态继续变化
```

这种方式有几个好处：

- 降低 token 浪费。
- 避免群聊爆炸。
- 保持成员响应有明确理由。
- 让群主更容易控制节奏。
- 为后续条件触发和自动调度打基础。

当前代码中 @mention 唤醒已经存在，但更完整的方向应当是把 TODOboard 状态变化也纳入唤醒来源。

### 4. 群组作为协作协议

群组需要一套明确协议，而不是只靠自然语言聊天。

建议的协作协议包括：

- 任务创建：谁可以创建任务，任务需要哪些字段。
- 任务领取：Agent 如何声明自己负责某个任务。
- 进度更新：什么时候更新状态，更新到哪里。
- 阻塞上报：无法推进时如何通知群主或用户。
- 交付提交：结果如何进入验收状态。
- 审查返工：谁能要求返工，返工原因如何记录。
- 完成归档：完成后如何沉淀经验。

这些协议不一定全部暴露给普通用户，但必须被系统内部理解。普通用户看到的是“群组在推进任务”，系统内部运行的是“Agent 围绕协议更新状态”。

### 5. 群组作为角色社会

CoBeing 的群组不是无人格工具池。每个成员都可以有自己的角色、表达方式、判断标准和工作偏好。

这带来一个重要差异：群组协作既要有秩序，也要保留角色个性。

过度流程化会变成企业工作流；过度人格化会变成混乱角色扮演。CoBeing 的技术难点是让 Agent 既像人一样有风格，又像系统组件一样可调度。

可以用三层约束解决（2026-08-05 起按人味分级）：

- 管家 `CHARACTER.md` 保留人格表达风格（用户入口的人味）。
- 执行型智能体 `EXPRESSION.md` 约束人味表达（像真人说话但无身份设定）。
- `JOB.md` 约束工作方式；Group 协作协议约束任务推进。

这样，执行者的效率与一致性不会被"角色扮演"拖累，管家作为唯一人格化入口的人味也不会被稀释。

### 6. 群组作为经验沉淀单元

很多任务经验不是单个 Agent 的，而是群组级的。

例如：

- 某类旅行规划适合哪些角色参与。
- 写作任务需要先研究再大纲再审稿。
- 用户不喜欢太正式的报告。
- 某个 Agent 在事实核查上表现稳定。
- 某个工具在某类任务中容易失败。

这些经验应该沉淀在 Group 或跨 Group 的经验层，而不是只写入单个 Agent 的记忆。

群组经验沉淀后，下次创建相似 Group 时可以复用结构、成员、TODOboard 模板和工作流程。

### 7. 纯 Prompt 驱动的协作策略（2026-06-09 更新）

群组协作采用纯 prompt 驱动策略，不引入重协议状态机。协作规则写入四个层级：

1. **群组 GUIDE.md**：定义本群组的场景、成员边界、协作风格、用户审批点、资源申请链和禁止行为清单。
2. **群主 HOST_JOB.md**：定义群主 9 项核心职责（标记任务始终、介入启动、恢复停滞、整合结果、申请资源、清理噪音、优化决策体验、维护 TODOboard、维护公共记忆）、8 种触发时机和 5 步判断框架。
3. **Agent 群组上下文**：每次群组唤醒时注入 6 步判断框架（职责→信息→用户判断→协作→资源→交付）、需用户判断的 7 类典型场景、需协作的 6 类典型场景、需资源的 4 类典型场景，以及禁止行为清单。
4. **工具说明**：`group-send` 明确为非阻塞协作旁路消息，发送后默认继续工作，使用 5 要素消息模板。

这套策略的核心是：**结构承载消息/唤醒/TODO/记忆/工具，prompt 承载判断——是否需要用户、是否需要协作、是否需要资源、是否应该继续。** 群主承担工作回合、成员分工、依赖路由和用户决策体验的组织责任；每个 TODO 是否自然续作由承担 Agent 先判断，再由群主承接跨成员、跨群组或需审批的后续请求。

- Butler 和 Host 作为核心 Agent。
- Agent 文件化职责与人味表达规范（EXPRESSION.md）+ 管家文件化人格（CHARACTER.md）。

- 插件、技能、MCP 基础设施。

### 仍需建设

这些内容更偏技术设想或待强化方向：

- TODOboard 统一数据模型与 GUI 看板。
- TODO 状态变化驱动 Agent 唤醒。
- 群主基于 TODOboard 的调度策略。
- 群组协作协议的工具化和强约束。
- 群组级经验模板复用。
- 工具智能体的统一注册、发现、调用评估和前端/日志可见性区分机制。
- 管家根据用户需求创建或推荐 Agent/Group/Skill/Plugin 的策略。

## 为什么这套技术有价值

单 Agent 的上限是“更聪明的助手”。多 Agent Team 的上限是“可组合的个人组织”。

CoBeing 的技术价值在于把普通用户从三个负担中解放出来：

- 不需要自己拆任务。
- 不需要自己管理多个工具。
- 不需要每次从零解释偏好和上下文。

管家负责入口，群组负责协作，通用智能体负责长期角色，工具智能体负责专业动作，TODOboard 负责状态和触发。五者组合起来，才有可能让普通用户真正拥有一个可持续工作的私人智能体团队。
