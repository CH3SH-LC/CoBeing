claw-code 单智能体编码能力调研：为什么一个 Agent Loop 就够了？

claw-code 是 Claude Code 的开源 Rust 重实现（由 UltraWorkers 维护），本质上是一个单智能体系统——
一个 API 调用循环 + 工具执行器。但它在编码和工程任务上表现出了极强的能力。
本文从架构设计、System Prompt 工程、工具体系、上下文管理、子代理委派、工程纪律六个维度分析其核心优势。

---

一、核心架构：精心设计的 Agent Loop

入口: rust/crates/rusty-claude-cli/src/main.rs (~11,500 行)
核心: rust/crates/runtime/src/conversation.rs — ConversationRuntime<ApiClient, ToolExecutor>

运行流程：

  用户输入 → 拼装 System Prompt → 发送给 LLM → 解析 SSE 响应流 →
      ├─ TextDelta → 追加到会话历史，继续接收
      ├─ ToolUse → PreToolUse Hook → 权限检查 → 执行工具 → PostToolUse Hook → 结果送回 LLM → 循环
      └─ MessageStop → 本回合结束

架构亮点：

  1. 泛型解耦: ConversationRuntime<C, T> — 提供商(Anthropic/xAI/OpenAI)和工具执行器可独立替换，
     不绑定特定 LLM 或工具实现。

  2. 自动压缩: 会话超过可配置的 token 阈值(默认 100K)时，自动压缩中间消息，
     保持上下文窗口有充足余量。压缩不是简单的截断，而是保留首尾、摘要中间。

  3. 超时恢复: 工具执行后如果模型在 POST_TOOL_STALL_TIMEOUT(10秒)内没有响应，
     断开连接并重新发送一次作为恢复尝试。

  4. 会话持久化: 每次工具执行后自动将消息追加到 .claw/sessions/ 下的 JSONL 文件。
     崩溃后恢复会话，不丢进度。

  5. 安全边界: 每一轮检查 max_iterations 防止无限循环；
     文件操作检查工作区边界、符号链接逃逸、目录遍历攻击。

二、System Prompt 工程：精确的行为约束是核心壁垒

位于 rust/crates/runtime/src/prompt.rs 的 SystemPromptBuilder 是整个系统最值得学习的设计。
它不是"你是一个编码助手"式的泛泛描述，而是一套精密的行为规范：

核心指令示例（从源码提取）：

  "你是一个交互式代理，帮助用户完成软件工程任务"
  "先读相关代码再动手改，改动严格限定在请求范围内"
  "不要添加推测性抽象、兼容性填充或无关清理"
  "如果方法失败了，先诊断原因再换策略——不要盲目重试"
  "忠实报告结果：验证失败就说失败，不要粉饰过去"
  "默认不写注释。只有当 WHY 不明显时才加一行——不写多行 docstring"
  "三个相似的写法好过一个过早的抽象"
  "只在实际需要的边界处做校验（用户输入、外部 API），不校验内部调用"

动态上下文注入：

  1. 环境信息: 工作目录、日期、平台(OS/Shell)
  2. CLAUDE.md 发现链: 从当前目录递归向上查找 CLAUDE.md / CLAUDE.local.md / .claw/CLAUDE.md
     这些文件包含项目级指令、编码规范、架构约束，自动注入到 System Prompt 中
  3. Git 状态: 当前分支、未提交变更、最近提交记录
  4. 去重与截断: 多个 CLAUDE.md 文件中重复的内容自动去重；
     每个文件最多 4000 字符，所有指令文件总共最多 12000 字符

这意味着每次编码对话，模型都拥有了项目的完整"宪法"——不仅知道要做什么，还知道
在这个特定项目中怎么做、有什么约束。这也是为什么单 Agent 能在不同项目中始终保持
一致的编码质量：上下文信息的密度和精准度远高于"裸"模型。

三、工具体系：40 个工具覆盖编码全流程

工具定义位于 rust/crates/tools/src/lib.rs，每个工具有名称、描述、JSON Schema 输入、
所需权限级别。

核心编码工具（读/写/执行）：

  | 工具          | 关键设计                                              |
  |---------------|-------------------------------------------------------|
  | read_file     | 偏移量+行数限制，10MB上限，二进制检测，工作区边界验证 |
  | write_file    | 完整文件写入，返回 diff，10MB上限                      |
  | edit_file     | old_string→new_string 精确替换，支持 replace_all       |
  | glob_search   | 基于 glob，支持大括号展开 {cs,tsx,uss}，递归通配符     |
  | grep_search   | 基于 ripgrep，支持正则、上下文行、文件类型过滤、多行   |
  | bash          | 超时/后台/沙箱(Linux unshare)/网络隔离                 |
  | PowerShell    | Windows 原生 PowerShell 支持                           |

关键洞察: edit_file（精确字符串替换）是编码任务中最重要的工具设计。
它要求模型精确指定 old_string，这意味着：
  - 模型必须先读取文件内容(grep/read_file)→确保 old_string 精确匹配
  - 替换失败会报错，倒逼模型重新审视上下文
  - 对比 write_file 全量覆写，edit_file 的变更粒度更细、更安全、更可审查

搜索工具的设计同样精巧：
  - glob_search + grep_search 组合使用：先用 glob 定位候选文件，再用 grep 精确定位
  - grep 支持 output_mode(content/files_with_matches/count) 适应不同查询阶段
  - head_limit/offset 分页机制防止大结果集撑爆上下文

Web 与交互工具：

  | 工具             | 用途                                      |
  |------------------|-------------------------------------------|
  | WebFetch         | 获取 URL 内容并提取信息                    |
  | WebSearch        | 搜索网络获取最新信息（文档/issue/方案）    |
  | AskUserQuestion  | 向用户提问澄清需求                         |
  | Skill            | 加载技能定义文件                          |

任务编排工具：

  | 工具           | 用途                                              |
  |----------------|---------------------------------------------------|
  | TaskCreate     | 创建结构化任务，含标题/描述/依赖关系               |
  | TaskGet/List   | 查询任务状态、列出所有任务                         |
  | TaskUpdate     | 更新任务状态(pending→in_progress→completed)        |
  | TaskOutput     | 获取后台任务的 stdout/stderr                       |
  | CronCreate     | 定时调度（cron 表达式），支持一次性+周期            |
  | RunTaskPacket  | 结构化任务包（含目标/分支策略/验收测试/提交策略）   |

子代理工具：

  | 工具         | 用途                                                   |
  |--------------|--------------------------------------------------------|
  | Agent        | 启动专门子代理处理独立任务（探索/审查/规划/执行等类型）|
  | TeamCreate   | 创建多代理团队                                         |
  | TeamDelete   | 删除团队                                               |

MCP 工具：

  | 工具              | 用途                                  |
  |-------------------|---------------------------------------|
  | MCP               | 在 MCP 服务器上执行工具               |
  | ListMcpResources  | 列出 MCP 资源                         |
  | ReadMcpResource   | 读取 MCP 资源                         |
  | McpAuth           | MCP 认证                              |

Worker 工具（完整生命周期管理）：
  WorkerCreate / WorkerGet / WorkerObserve / WorkerResolveTrust /
  WorkerAwaitReady / WorkerSendPrompt / WorkerRestart / WorkerTerminate /
  WorkerObserveCompletion

  Worker 的生命周期状态机: Spawn→TrustRequired→ReadyForPrompt→Running→Finished/Failed
  这比简单的 "Agent" 工具更精细——需要信任门控、就绪等待、观察完成，适用于
  更严谨的自主协调场景。

工具执行流程（tools/src/lib.rs execute_tool()）:
  1. 权限检查 — maybe_enforce_permission_check() 对照 PermissionEnforcer
     bash/PowerShell 的权限按命令内容动态分级（只读命令 vs 破坏性命令不同要求）
  2. 执行 — 路由到具体实现函数
  3. 结果返回 — 结构化输出，含 exit code / stdout / stderr / 截断标记

四、权限系统：按操作动态分级

位于 rust/crates/runtime/src/permission_enforcer.rs

三种模式：
  - ReadOnly        — 读文件、搜索、WebFetch
  - WorkspaceWrite  — 写文件、编辑文件
  - DangerFullAccess — bash、PowerShell、子代理

bash 权限动态分级：
  不是简单地"bash = 危险"，而是分析命令内容：
    - 只读命令(find/grep/cat -n/ls/git log/...) → 降级为 ReadOnly
    - 破坏性命令(rm -rf/git push --force/...) → 需要 DangerFullAccess
    - 模糊命令(可能读可能写) → 按 DangerFullAccess 处理
  这比 CoBeing 的 "workspace-write / ask" 二元模式精细得多。

五、子代理委派：单智能体的"兵力倍增器"

claw-code 虽然本质是单 Agent Loop，但通过子代理系统实现了并行和委派：

  1. Agent 工具: 启动专门子代理（explore 代理做代码搜索、code-reviewer 代理做审查、
     plan 代理做方案设计）。主 Agent 不直接处理大量搜索结果，而是委托子代理——
     保护了主 Agent 的上下文窗口不被大量搜索输出撑爆。

  2. Worker 系统: 比 Agent 更精细——需要信任门控(TrustRequired→ResolveTrust)、
     就绪等待(AwaitReady)、发送提示(SendPrompt)、观察完成(ObserveCompletion)。
     适用于需要持续监控的长时间任务。

  3. Task 系统: 后台任务创建/监控/输出获取，支持依赖关系(blocks/blockedBy)。
     任务状态机: pending→in_progress→completed

  4. Team 系统: 多代理团队的创建和删除，用于并行执行独立任务。

  5. CronCreate: 定时调度（cron 表达式），一次性提醒或周期任务。

这些子代理机制的核心价值不是"多 Agent 协作"，而是：
  - 上下文隔离: 搜索结果不会撑爆主 Agent 的上下文窗口
  - 并行执行: 多个独立子任务可以同时进行
  - 专门化: 不同类型的子代理有不同的 system prompt 和行为模式(explore/plan/review)

---

六、上下文管理：让有限上下文窗口装下最大有效信息

这是单 Agent 系统最核心的竞争力。claw-code 做对了几件事：

  1. 动态注入而非静态预设: 不是给模型一段固定的"你是编码助手"prompt，
     而是每次会话启动时动态拼装——项目指令(CLAUDE.md)、Git 状态、平台信息、
     当前日期，全部是活的、最新的。

  2. 分层指令发现链:
     当前目录/.claw/CLAUDE.md
     → 当前目录/CLAUDE.md
     → 父目录/CLAUDE.md
     → ...直到根目录
     → 当前目录/CLAUDE.local.md (不提交 git，个人偏好)
     这确保了无论从哪个子目录启动，模型都能获得完整的项目级指令。

  3. 去重与截断: 多个文件中的重复内容自动去重（节省 token）；
     每个文件最多 4000 字符（防止单个大文件霸占 prompt）；
     所有指令文件总共最多 12000 字符（留足空间给对话和工具结果）。

  4. 自动压缩: 会话 token 超过阈值时压缩中间消息，不是简单丢弃——
     保留首条(系统指令)、最近消息(当前上下文)、关键转折点。

  5. 提示缓存: 利用 Anthropic 的 prompt caching，对不变部分(System Prompt +
     CLAUDE.md + Git Status)自动缓存，大幅降低重复发送的成本。

与 CoBeing 的对比：
  CoBeing 的 Agent 也有 System Prompt 拼装(prompt-builder.ts)，但指令的精确度、
  去重截断机制、以及动态环境信息(Git/CLAUDE.md链)的注入密度都不如 claw-code。

七、工程纪律：不是"能跑就行"

claw-code 的工程文化比技术设计更值得学习：

  1. PARITY.md: 逐项追踪 Rust 实现与原 TypeScript 版本的差异——
     每个功能标记为 ✅已实现 / ⚠️部分 / ❌缺失，而不是模糊的"基本完成了"

  2. ROADMAP.md: ~580 行，每个问题都记录了根因分析、修复方案、影响范围。
     例如 #38 健康探测——"被压缩的对话加载后可能跳过完整轮次，
     根本原因是压缩后的 token 计数与模型预期的对话历史不一致"

  3. Mock 测试基础设施: mock-anthropic-service crate——
     确定性模拟 API 服务，10 个脚本化场景覆盖全工具工作流，
     包括流式文本、权限提示、工具使用、错误恢复。
     没有真实的 API 调用也能验证整个 Agent Loop 的行为正确性。

  4. JSON 输出模式: 所有 CLI 命令支持 --output-format json，
     这意味着 claw-code 不仅是一个交互式工具，也是 CI/CD 流水线中的
     可编程组件——可以被其他脚本或 Agent 调用并解析输出。

  5. 多提供商路由: ProviderClient 枚举通过模型名称前缀自动路由——
     anthropic/ → Anthropic, grok → xAI, openai/gpt- → OpenAI Compat,
     qwen/ → DashScope。单 Agent 框架不绑定单一 LLM 提供商。

八、对 CoBeing 的关键启示

claw-code 作为单智能体比 CoBeing 多智能体编码能力更强，核心原因不是 Agent 数量，
而是以下设计差距：

  1. System Prompt 的精确度
     claw-code: 大量精确行为约束（不画饼、先读再改、失败了诊断根因、不写无用注释）
     CoBeing: Agent 的 SOUL.md/AGENTS.md 偏重"角色扮演"和"协作方式"，
     缺少对编码行为本身的精确约束（如"读文件后才能改""不要推测性抽象"）

     建议: 为编码类 Agent 增加专门的 coding-behavior 规则模板，
     参照 claw-code 的指令风格，精确约束代码修改行为。

  2. 工具的质量而非数量
     claw-code 的 edit_file（精确字符串替换）设计精良：
     - 必须精确匹配 old_string → 倒逼模型先读文件
     - 替换失败报错 → 倒逼模型重新审视上下文
     CoBeing 的 write_file/edit_file 缺少这种"倒逼正确性"的设计约束。

     建议: 增强 edit_file 工具，要求 old_string 精确匹配，
     匹配失败时报错并提示重新读取文件。

  3. 子代理是上下文管理手段，不是多 Agent 架构
     claw-code 的 Agent/Worker 子代理本质上是"把大搜索结果隔离到子上下文，
     保护主 Agent 的上下文窗口"。CoBeing 的多 Agent 群组协作
     (WakeSystem + group-send) 是真正的多 Agent 协作——但上下文隔离
     恰恰不如 claw-code 的子代理干净。

     建议: 为 CoBeing Agent 增加"委派子任务到临时 Agent"的能力，
     子 Agent 完成后只回传摘要，不回传完整工具调用链。

  4. 上下文管理 = 信息密度 × 信息质量
     claw-code 的动态注入(CLAUDE.md链 + Git + 环境)让模型每次对话
     都拥有项目的"完整宪法"。CoBeing 的 Agent 唤醒时注入的是
     PROGRESS.md + INTERFACE.md + 群组上下文，偏重"协作状态"但
     缺少"项目编码规范"。

     建议: 在 Agent 唤醒时增加编码规范层（如 .cursorrules / CLAUDE.md 发现链），
     让每个 Agent 都知道项目的编码约束。

  5. 工具权限应该动态分级
     claw-code 的 bash 权限按命令内容动态分级（读/写/危险），
     CoBeing 的权限是 workspace-write / ask 二元模式。
     这种粗粒度的权限导致要么完全信任、要么完全阻止，
     无法支持"允许读但不允许写"的中间状态。

     建议: 对 bash 命令增加动态权限分析——只读命令自动放行，
     写操作命令需要确认，破坏性命令需要显式批准。

  6. 工程纪律是保持质量的前提
     claw-code 的 PARITY.md + ROADMAP.md + Mock 测试，
     每个功能都有明确的状态追踪和测试覆盖。
     CoBeing 的 PROGRESS.md 是事后记录而非事前设计追踪。

     建议: 建立功能对等性追踪矩阵(类似 PARITY.md)，
     标记每个功能的实现状态/测试覆盖/文档状态。

---

九、总结

claw-code 用"一个精心设计的 Agent Loop + 40 个高质量工具 + 精密 System Prompt +
智能子代理委派 + 严格工程纪律"证明：单智能体完全可以在编码任务上达到很高的水平。

它的成功不在 Agent 的数量，而在：
  - 每个设计决策都有明确的 WHY（ROADMAP.md 的问题根因分析）
  - 每个工具都被精心设计为"倒逼正确性"（edit_file 强制精确匹配）
  - System Prompt 不是泛泛的"你是编码助手"，而是精确到具体行为约束
  - 上下文管理是系统工程，不是简单的"多读几个文件"
  - 子代理是上下文管理手段，不是架构目的

CoBeing 作为多 Agent 框架，可以在这些基础上更进一步——每个 Agent 拥有 claw-code 级别
的单体能力 + Agent 之间的协调 = 质的飞跃。但前提是先把单 Agent 的基本功（System Prompt
精确度、工具设计质量、上下文管理密度）做到 claw-code 的水平。
