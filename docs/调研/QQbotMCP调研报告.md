### 💎 报告摘要与分析总结
本报告旨在为QQ Bot与本地MCP服务器的开发提供技术备查。核心结论如下：

*   **接口能力与限制**：官方API已开放消息、群组、用户、富媒体等核心能力。但**频控机制**（如单聊每月4条主动消息、被动回复5条/次）和**文件类型限制**（仅支持`pdf`、`doc`、`txt`）是技术上最关键的制约点。
*   **构建MCP服务器的官方依据**：`MCP`（Model Context Protocol）属于你本地的服务封装层。你**无需寻找官方"MCP接口"**，只需根据官方提供的**HTTP API**、**WebSocket/Webhook**等标准接口进行二次封装即可。
*   **潜在的技术障碍与规避路径**：
    *   **公网接入隐患**：官方主要推荐基于Webhook、要求公网IP/域名的内网穿透方案。但这可能引入不必要的网络暴露风险，不符合你的"本地"需求。
    *   **本地化部署的必然选择**：为完全规避公网要求，你的"本地Agent MCP服务器"应选用**WebSocket模式**。这允许你的本地服务器主动发起连接，无需公网IP，更符合你的开发场景。
*   **技术栈与工具链建议**：初期封装首选社区维护良好、示例丰富的 **`qg_botsdk`** 等Python SDK，可快速完成Bot逻辑开发。Agent集成则推荐用 **`FastMCP`** 或 **`LangChain`** 进行MCP化包装，便于和主流AI模型协作。

### 🧩 一、官方接口与功能全景图谱
官方API主要基于**RESTful HTTP**和**WebSocket**协议，功能矩阵如下：

| 功能模块 | 核心API接口/事件 | 关键能力与限制（来源引用） |
| :--- | :--- | :--- |
| **消息发送** | `POST /v2/users/{openid}/messages`<br>`POST /v2/groups/{group_openid}/messages` | - **频控限制**：单聊主动推送 **每月4条**，被动回复 **5分钟内最多5条**；群聊主动推送 **每月4条**，被动回复 **5分钟内最多5条**。<br>- **在线要求**：发送消息接口要求机器人必须保持WebSocket连接。<br>- **URL限制**：消息内含URL需提前在后台配置白名单，否则发送失败。 |
| **消息接收** | `C2C_MESSAGE_CREATE` (事件类型)<br>WebSocket/Webhook | - **不保证有序**：官方不保证消息推送的严格顺序，必要时需开发者自行缓冲、排序。<br>- **消息排重**：同一`msg_id`的消息可能重复推送，需开发者实现去重逻辑。 |
| **群组管理** | `POST /v2/groups/{group_openid}/members/{member_openid}/roles` 等 | - **权限前提**：踢人、禁言等管理操作，需先将机器人设为**群管理员**。<br>- **官方API能力**：官方提供基础的群消息撤回接口 `POST /v2/groups/{group_id}`。但更多高级功能（如设置公告、全员禁言）在官方文档中未明确列出，通常由 **NapCatQQ** 等第三方框架提供。 |
| **频道管理** | `GET /guilds/{guild_id}` | - **权限前提**：频道管理操作，需为机器人在对应子频道分配**管理员权限**。<br>- **限频策略**：文字子频道默认每天向 **2个** 子频道推送各 **20条** 消息，每秒最多 **5条**；频道私信每天对一个用户发 **2条**，每日累计 **200条**。 |
| **富媒体消息** | 附件字段 `attachments` (事件接收)<br>`POST /v2/groups/{group_openid}/files` | - **文件类型限制（关键）**：机器人**仅支持接收** `pdf`、`doc`、`txt` 格式的文件。<br>- **大小限制**：图片30MB，视频100MB，文件100MB，语音20MB。<br>- **发送方式**：发送富媒体时，`srv_send_msg = true` 会**直接发送并占用主动消息频次**。 |
| **用户与关系** | 获取用户信息、添加/删除好友等 | - **开放性**：能力分散在"用户管理"等事件或端点，开发者可根据需求调用。 |
| **主动消息与召回** | `is_wakeup` 字段 (C2C发消息) | - **互动召回消息**：用户主动对话后，机器人可在 **未来30天内** 的4个周期内，每周期下发 **1条** 互动召回消息。<br>- **消息撤回**：支持撤回已发送的消息。 |

### 🛠️ 二、MCP服务器构建的关键路径与推荐工具链

#### 1. 核心路径：WebSocket模式是你的最佳选择
实现“本地部署”的关键在于选用**WebSocket**连接方式。

*   **原理与优势**：你的本地服务器作为客户端，**主动**与QQ服务器建立并维持长连接。这完全**不需要**你拥有公网IP或域名，所有数据交换均通过这条主动建立的通道完成，不依赖第三方穿透服务。
*   **具体步骤**：
    1.  **获取接入点**：调用 `GET /gateway/bot` 接口，获取一个形如 `wss://api.sgroup.qq.com/websocket/` 的通用WebSocket地址。
    2.  **建立连接与认证**：你的MCP服务器用此地址建立WebSocket连接，成功后进行协议要求的鉴权。
    3.  **交互收发**：连接建立后，你只需通过此连接 `send` 消息，并监听 `on_message` 事件，即可完成所有消息的收发。

#### 2. 官方及生态工具链速览
为加速开发，可选用以下成熟工具：

*   **官方参考**：官方提供部分语言的SDK和WebSocket接入文档，是理解协议的基础。
*   **Python SDK**：社区维护的 **`qg_botsdk`** 是当前主流选择，它封装了上述复杂的WebSocket握手和API调用，代码简洁，可使你专注于业务逻辑。
*   **全能框架**：**NoneBot2**、**AstrBot**、**OpenClaw** 等框架功能更全面，它们已内置Bot连接和消息处理，你只需编写少量插件代码，能大幅简化开发流程。
*   **底层实现补充**：官方没有面向个人的“好友关系”API，如果你需要这个层面的功能，**NapCatQQ** 等基于NTQQ协议的非官方框架提供了底层接口，是官方API之外的有力补充。

#### 3. MCP化包装与Agent集成建议
构建MCP服务器的核心，是把你对QQ API的调用封装成“工具（Tools）”。

*   **工具封装示例**：
    *   **文本收发**：封装为 `qq_send_message`、`qq_receive_message`。
    *   **群组管理**：封装为 `qq_kick_member`、`qq_mute_member`。
    *   **文件处理**：封装为 `qq_download_file`、`qq_upload_group_file`。
*   **Agent集成与调用**：在Agent端（如LangChain），配置好指向你本地MCP服务器的客户端后，Agent即可自主调用这些QQ工具，实现“说人话，办QQ事”。
