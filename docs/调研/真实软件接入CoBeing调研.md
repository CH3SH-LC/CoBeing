# 真实软件接入 CoBeing 调研

> 创建：2026-08-12
> 定位：CoBeing 从「抽象工具」扩展到「真实工作」的第一步调研——列举电脑常用软件及涉及的工作，判断各自能否作为 CoBeing 扩展接入，落在哪一层，优先级如何。
> 关联文档：`办公软件MCP调研报告.md`（office MCP 实现技术栈）、`项目现状.md`、`架构说明.md`、`产品战略.md`

---

## 一、核心判断

CoBeing 现在缺的不是「插件」，是「感官」——它内部世界是自洽的（Agent 互相协作、TODO、工作区），但它看不见用户真实生活里的数据（微信、邮件、日历、网盘、浏览器），也没有手脚伸进真实应用干活。

「扩展到真实工作」的本质是给 CoBeing 装上：
- **眼睛/耳朵**：从真实世界读数据（消息、邮件、文档、日历、网页）
- **手/脚**：往真实应用执行动作（生成文档、整理文件、填表单、发消息）

好消息：现有扩展架构的分层已经够用，不是从零造。关键决策是**每个软件落在哪个抽象层**，而不是「要不要做成插件」。

---

## 二、接入模式四分法（决定「接哪一层」）

CoBeing 的插件不是一种抽象，是分层。真实软件接入按交互模式落在不同层（这些层代码里均已存在）：

| 模式 | 场景 | 落层 | 现有基础 |
|---|---|---|---|
| **A. 双向对话** | 消息进来 → Agent 理解并回复 | `Channel`（`packages/channels` 的 `ChannelAdapter`） | QQ Bot channel 已有雏形 |
| **B. 执行动作** | Agent 调工具 → 在真实应用里干活并返回结果 | `MCP server`（`packages/mcp-servers`）/ Tool 插件 | office MCP（docx/xlsx/pptx）、claude-code MCP 已有 |
| **C. 单向数据源** | 按需/定时读取真实数据进 CoBeing | MCP server（read 工具） | 基本空白，需新建 |
| **D. 事件触发** | 外部事件 → 唤醒 Agent 或提醒用户 | Channel onMessage / TODO 触发器 | 已有部分（TODO 触发、用户唤醒） |

判断「某软件能不能接入」= 先问：**它是要「对话、干活、读取、还是通知」？**
同一个软件可能同时落多层（如邮件既是数据源 C 也是回复的 Channel A）。

插件 SDK 已支持的注册类型（`packages/plugin-sdk/src/types.ts`）：
`model-provider` / `channel` / `tool` / `memory-backend` / `extension`，并可注册 hook、prompt layer、skill、toolagent、UI extension。

## 三、电脑常用软件全景 × 接入判断

### 通讯社交类

| 软件 | 涉及的工作 | 模式 | 可行性判断 |
|---|---|---|---|
| **微信** | 读聊天记录、回复消息、收文件 | A/C | ⚠️ **最高风险**。个人号无官方 API，逆向协议有封号+合规风险；**企业微信**有官方 API 可行。必须先定边界 |
| **QQ** | 群管理、群消息、群秩序 | A | ✅ **最可行**。官方 QQ 机器人 API，channel + MCP 雏形已存在（`channels/qq` + `mcp-servers/qqbot`），等于补完已有能力 |
| **邮件**（Outlook/QQ邮箱/网易） | 收件归类、自动回复、归档 | A/C | ✅ 可行。IMAP/SMTP 标准协议，安全可控，是「帮我处理邮件」的强需求 |
| **钉钉/飞书** | 工作消息、日程 | A | 🟡 有开放 API，企业场景价值大 |
| Telegram/WhatsApp | 国际通讯 | A | ✅ 标准 Bot API，个人开发者友好 |

### 办公文档类

| 软件 | 涉及的工作 | 模式 | 可行性判断 |
|---|---|---|---|
| **Word/Excel/PPT** | 生成、编辑、公文排版 | B | ✅ **已有 office MCP**。**缺口**：docx 只有「从零创建」没有「打开已有文件编辑」（excel 有 `office_excel_open`，word 没有）——真实工作大量是改既有文档，需补 |
| **PDF** | 读取、合并、转换 | B | 🟡 需新建（pdf-lib/pandoc），中优先级 |
| **笔记**（Obsidian/本地 md/OneNote/Notion） | 知识库读写、整理 | B/C | 🟢 **被低估的高价值项**。Obsidian/本地 md 就是 markdown，与 CoBeing 文件工具天然同构，几乎零成本——「把笔记变成 Agent 能读写的记忆」 |

### 浏览器/网页类

| 软件 | 涉及的工作 | 模式 | 可行性判断 |
|---|---|---|---|
| **Chrome/Edge** | 查资料、填表单、截图、下载 | B/C | ✅ **最高频真实需求**。Playwright 驱动的浏览器 MCP 是标准方案，让 Agent「看网页、点按钮、存结果」 |
| **网盘**（百度/阿里/OneDrive） | 文件上传下载整理 | C | 🟡 各家有 API，但认证与限速是坑 |
| 购物/内容平台（淘宝/小红书/知乎/抖音） | 信息采集、比价 | C | 🟡 无官方 API，靠浏览器自动化，弱合规 |

### 系统/个人事务类

| 软件 | 涉及的工作 | 模式 | 可行性判断 |
|---|---|---|---|
| **文件管理器** | 整理归类、改名、归档 | B | ✅ 文件工具已存在，缺的是「绑定用户真实文档目录」这层 |
| **系统日历/提醒** | 日程管理、定时唤醒 | C/D | ✅ 中优先级，「帮我安排明天」是管家核心场景 |
| **截图/OCR** | 图片文字提取 | B | 🟢 低成本高感知（Tesseract/系统 OCR） |
| **记账/财务** | 账单归类、汇总 | C | 🟡 各家无统一 API，需人工导出 |
| **音乐/媒体** | 播放控制、推荐 | B | 🟢 锦上添花 |

### 开发者类

| 软件 | 涉及的工作 | 模式 | 可行性判断 |
|---|---|---|---|
| **编码/Git** | 编码任务、代码审查 | B | ✅ **已有 claude-code MCP**（委托真实编码循环），已是最成熟的真实接入 |

## 四、优先级判断

判断标准：**能否直接证明「用户少打开几个 App」+ 技术风险可控 + 数据合规**（而非「哪个酷」）。

**P0 —— 立刻做，直接证明价值：**
1. **浏览器 MCP** — 真实生活里最高频的「帮我查/帮我填/帮我抓」入口，是 CoBeing 从自洽世界伸向真实世界的第一只手。
2. **邮件接入** — 标准协议、安全可控，「处理邮件」是强需求，能证明「事务处理」闭环。
3. **QQ channel 补完** — 用户明确提到的「管理QQ群」，且代码已有一半，等于收尾而非从零。
4. **本地文档/笔记目录绑定** — 成本最低、与现有文件工具同构，让 Agent 直接读写用户真实的工作文档。

**P1 —— 有价值但先定边界：**
5. **微信** — 必须先确认路线（个人号只读逆向 ⚠️ / 企业微信官方 API / 放弃），这是合规问题不是技术问题。
6. **Office 补缺口** — office MCP 已有，补「打开已有 docx 编辑」即可接真实公文场景。
7. **日历/日程**。

**P2 —— 锦上添花：** OCR、音乐、记账、笔记知识库。

---

## 五、战略问题

按产品愿景（「用户少打开几个 App」「把重复事务交给长期记忆的 Agent」），最核心的一跳不是接多少软件，而是接 **「用户的个人数据层」**——本地文档、笔记、日历、通讯记录。

这决定了 Agent 是「有记忆的真人同事」（读得到用户过往与上下文）还是「每次从零的临时工具」（只活在 CoBeing 内部）。

---

## 六、下一步建议

挑一个 P0 项（倾向浏览器 MCP 或邮件）走通「真实数据 → Agent → 真实动作 → 用户确认」的完整链路，用它验证「插件如何落入现有分层架构」，再批量复制到其他软件。
